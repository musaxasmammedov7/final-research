\begin{abstract}
Standard Kubernetes deployments treat container instances as disposable, stateless entities. When an underlying node enters maintenance (\texttt{kubectl drain}) or an Amazon Web Services (AWS) EC2 Spot instance is reclaimed via a two-minute interruption notice, the Kubernetes scheduler terminates running pods with a \texttt{SIGKILL} signal. Consequently, 100\% of volatile in-memory heap state, in-flight transaction logs, and TCP socket descriptors are irrevocably destroyed, resetting the process state to zero ($R_{\text{state}} = 0\%$). To prevent state loss, engineering practice has historically resorted to external in-memory data grids (e.g., Redis clusters), incurring severe network serialization overheads (1--5~ms) and requiring intrusive application-level code modifications.

This paper proposes, implements, and empirically validates a fully automated, transparent live migration architecture for stateful Kubernetes workloads. Leveraging the Linux kernel Checkpoint/Restore in Userspace (CRIU) subsystem, Kubelet Checkpoint API (KEP-2008), OCI layer packaging via Buildah, the CRI-O container runtime, and a sidecar-free Cilium eBPF Service Mesh, our system preserves 100\% of runtime volatile memory ($R_{\text{state}} = 100\%$) across physical AWS EC2 worker nodes without requiring a single line of application source code refactoring. Empirical evaluation conducted on a multi-node AWS EC2 cluster under continuous 50~Hz external HTTP probing demonstrates that our architecture achieves a median client-observed downtime ($T_{\text{blackout}}$) of 797--1078~ms, outperforming native Kubernetes cold eviction (1289~ms) while completely eliminating data loss.
\end{abstract}

\section{Introduction}
Container orchestration systems, spearheaded by Kubernetes, have revolutionized modern cloud infrastructure through declarative scheduling, horizontal scaling, and immutable infrastructure patterns \cite{burns2016borg}. However, Kubernetes was fundamentally architected under the assumption of stateless microservice idempotency. When an infrastructure hazard occurs---such as scheduled Linux kernel upgrades, node draining, hardware degradation, or cloud Spot instance preemption---the control plane executes a cold eviction: it terminates the pod with \texttt{SIGKILL} and schedules a replacement instance from a pristine container image.

For stateful workloads, including dedicated multiplayer game servers (e.g., Counter-Strike, Minecraft), in-memory video encoding pipelines, financial risk models, and streaming inference servers, volatile RAM contains irreplaceable state accumulated over hours of computation. A cold restart causes complete state obliteration ($R_{\text{state}} = 0\%$), resulting in severed client sessions, dropped WebSocket connections, and extensive compute waste.

While external distributed caching (e.g., Redis, Memcached) is widely adopted to decouple state, it introduces significant trade-offs:
\begin{enumerate}
    \item \textbf{Latency Amplification:} Inter-process communication over TCP/IP introduces 1--5~ms of round-trip latency, compared to $\approx 100$~ns for direct CPU memory bus access.
    \item \textbf{Intrusive Refactoring:} Legacy binaries, simulation software, and complex monolithic runtimes cannot easily be refactored to offload internal pointer graphs to key-value stores.
    \item \textbf{Infrastructure Cost:} Running highly available, clustered Redis deployments with replication substantially increases total cost of ownership (TCO).
\end{enumerate}

To address these limitations, we design and evaluate a zero-code-change live migration architecture in Kubernetes. By orchestrating CRIU memory snapshots into standard OCI registry layers and decoupling layer-7 routing from container boundaries via node-level Cilium eBPF socket maps, our approach achieves sub-second client blackouts while guaranteeing 100\% volatile memory preservation.

\subsection{Core Technology Stack}
The architectural pipeline integrates five foundational Linux and Kubernetes primitives:

8. \textit{Socket Activation:} Process resumes execution on target port \texttt{:8090} with identical memory heap. \\

\begin{itemize}
    \item \textbf{CRIU (v3.16.1):} Interacts with kernel interfaces (\texttt{ptrace}, \texttt{/proc/PID/pagemap}, \texttt{userfaultfd}) to freeze process trees and capture address spaces, registers, and file descriptors into binary image archives (\texttt{pages-1.img}, $\approx 26$~MB).
    \item \textbf{Kubelet Checkpoint API (KEP-2008):} Authenticated endpoint on port 10250 exposing container freezing without node cordon.
    \item \textbf{Buildah \& Local Registry:} Packages memory dumps into standard OCI images tagged with \texttt{io.kubernetes.cri-o.annotations.checkpoint.name}.
    \item \textbf{CRI-O Runtime (v1.31):} Reads OCI checkpoint annotations and invokes \texttt{runc/criu restore} directly into volatile host memory.
    \item \textbf{Cilium eBPF Service Mesh:} Provides sidecar-free Layer-7 proxying via node-level Envoy daemons and kernel socket table retargeting (\texttt{BPF\_MAP\_TYPE\_SOCKHASH}).
\end{itemize}

\subsection{Overcoming the Sidecar Incompatibility Paradox}
Traditional Service Mesh implementations (e.g., Istio, Linkerd) inject an Envoy sidecar proxy into the pod namespace, intercepting local traffic via \texttt{iptables PREROUTING} rules over \texttt{127.0.0.1}. 

When CRIU attempts to freeze a multi-container pod containing an active sidecar proxy, unresolved in-pod loopback TCP sockets and local namespace routing tables cause CRIU to abort with fatal kernel errors. 

Our architecture completely eliminates intra-pod sidecars (Zero-Sidecar Mesh). By hosting a single shared Envoy instance per physical node and employing \texttt{bpf\_sockops} programs, socket redirection occurs entirely within kernel memory without traversing TCP/IP stacks or generating namespace-locked socket dependencies.

\section{Mathematical Latency \& Retention Model}
We formalize the performance of the migration pipeline by distinguishing total orchestration duration from client-observed blackout.

\subsection{Total Migration Pipeline Time}
The total orchestration latency $T_{\text{total}}$ comprises dump generation, container build, image push, and restoration:
\begin{equation}
T_{\text{total}} = T_{\text{dump}} + T_{\text{build}} + T_{\text{push}} + T_{\text{restore}}
\end{equation}

\subsection{Client-Observed Blackout Window}
Crucially, during $T_{\text{dump}}$, $T_{\text{build}}$, and $T_{\text{push}}$, the source container continues servicing inbound traffic (\texttt{KeepRunning: true}). The actual service unavailability ($T_{\text{blackout}}$) spans exclusively from the termination of the source pod to verified TCP reception on the target node:
\begin{equation}
T_{\text{blackout}} = T_{\text{restore}} + T_{\text{ebpf\_sync}}
\end{equation}
Because $T_{\text{ebpf\_sync}} < 2$~ms under Cilium eBPF, $T_{\text{blackout}} \approx T_{\text{restore}}$.

\subsection{State Retention Ratio}
State preservation is measured by the ratio of valid recovered heap memory pages $M_{\text{restored}}$ to snapshot pages $M_{\text{dumped}}$:
\begin{equation}
R_{\text{state}} = \frac{M_{\text{restored}}}{M_{\text{dumped}}} \times 100\%
\end{equation}
Under native Kubernetes eviction, $R_{\text{state}} \equiv 0\%$. Under our proposed CRIU architecture, $R_{\text{state}} \equiv 100\%$.

\section{Empirical Evaluation \& Experimental Results}

\subsection{Experimental Testbed}
The research testbed was deployed on AWS EC2 in region \texttt{eu-central-1} (Frankfurt) within a dedicated VPC (\texttt{10.10.0.0/16}):
\begin{itemize}
    \item \textbf{Control Plane:} 1x \texttt{c7i-flex.large} instance (2 vCPU, 4~GB RAM, Ubuntu 24.04, Linux Kernel 6.8).
    \item \textbf{Worker Nodes:} 2x \texttt{m7i-flex.large} instances (2 vCPU, 8~GB RAM, 10~Gbps VPC interconnect).
    \item \textbf{Workload:} A high-frequency in-memory stateful counter incrementing at 10~Hz, serving HTTP/1.0 state endpoints on port 8090, alongside the full 11-microservice Google Online Boutique suite.
\end{itemize}

\subsection{State Continuity \& Blackout Analysis}
The empirical data yields three paramount findings:
\begin{enumerate}
    \item \textbf{Sub-Second Downtime:} In Run 2, the client blackout was reduced to \textbf{797~ms}, which is \textbf{38.2\% faster} than standard Kubernetes cold eviction (1289~ms).
    \item \textbf{Zero Memory Obliteration:} Under native reschedule, the counter suffered total wipeout ($43544 \to 8$), confirming $R_{\text{state}} = 0\%$. Conversely, under CRIU migration, the counter smoothly continued across nodes ($51 \to 60 \to 57$ in Run 1; $77 \to 85 \to 79$ in Run 2), demonstrating 100\% state preservation.
    \item \textbf{Snapshot Variance:} The counter delta between kill and restore reflects background increments during image packaging while the source process remained active, validating the non-blocking nature of the pipeline.
\end{enumerate}

\section{Industrial Implications: Spot Instance Economics}
AWS EC2 Spot instances offer up to 70--90\% cost savings compared to on-demand pricing but are subject to preemption with a strict two-minute notification. Because our entire migration pipeline executes within \textbf{1.64--1.93 seconds} (well within the 120-second threshold), stateful services can safely operate on ephemeral Spot infrastructure, slashing cloud infrastructure expenditure without risking data loss.

\section{Conclusion}
This study presented a zero-loss stateful container live migration architecture in Kubernetes utilizing CRI-O, CRIU, and sidecar-free Cilium eBPF. The architecture achieves sub-second client blackouts (797~ms) and 100\% in-memory state preservation without modifying application source code. Future work will investigate dirty-page pre-copying techniques to further compress downtime below 200~ms.
