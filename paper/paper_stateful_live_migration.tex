\begin{abstract}
Stateful singleton containers lacking distributed replication---such as numerical solvers, in-memory stream aggregators, and warm ML inference caches---lose all volatile heap state during Kubernetes node drains and cloud Spot instance preemptions. We evaluate an automated, snapshot-consistent container live migration pipeline built upon CRIU (v4.3), the Kubelet Checkpoint API (KEP-2008), Buildah OCI packaging, CRI-O (v1.31), and host-level Cilium eBPF routing across a multi-node AWS EC2 cluster. Across $N = 36$ live migrations of a stateful service compared against $N = 20$ native cold reschedules, decoupled migration achieves a median cutover blackout of 1064.5~ms (mean $1132.4 \pm 241.1$~ms) versus 1019.0~ms (mean $1007.0 \pm 231.2$~ms) for cold restart---an overhead of only 45.5~ms (+4.5\%) while preserving process heap state. A two-sided Mann-Whitney U test confirms that cutover blackout does not differ significantly from cold restart ($U = 252.5, p = 0.0660$), with variance in both cases governed by Kubelet's 1~s PLEG relist cycle. In decoupled mode, the service incurs bounded state drift of 669.0~ms ($7.5 \pm 0.6$ updates at 10~Hz), whereas synchronous stop-and-copy yields zero drift at the cost of extending blackout to 1.88~s. Scaling numerical heaps to 1024~MB (1~GB) verifies 100\% bit-exact SHA-256 integrity within 50.09~s (41.7\% of the 120~s Spot SLA), where disabling Buildah compression slashes packaging from 34.02~s to 13.74~s. Finally, empirical sidecar probing demonstrates why single-container KEP-2008 checkpoints rupture in-pod loopback proxies, validating host-level eBPF routing.
\end{abstract}

\section{Introduction}
Kubernetes manages workloads under the foundational assumption that container instances are ephemeral and stateless \cite{burns2016borg}. When worker nodes undergo kernel maintenance (\texttt{kubectl drain}) or cloud virtual machines are reclaimed, stateless microservices maintain availability by spinning up replacement replicas before terminating old instances (\texttt{maxSurge}).

However, critical production classes maintain large, mutable in-memory heaps without built-in distributed consensus:
\begin{enumerate}
    \item \textbf{Scientific \& Numerical Solvers:} Iterative physics simulations, linear algebra solvers, and legacy C++/Python runtimes accumulating state over hours.
    \item \textbf{Warm ML Inference Caches \& Aggregators:} High-dimensional embedding buffers, key-value transformer caches, and session aggregators where rebuilding state from cold storage imposes severe warm-up latency.
\end{enumerate}

Deploying these workloads on Amazon Web Services (AWS) EC2 Spot instances yields 70--90\% compute cost savings, but subjects pods to abrupt reclamation with a 120-second termination notice \cite{netflix_spot, aws_spot}. Standard eviction issues \texttt{SIGTERM} followed by \texttt{SIGKILL}, destroying volatile RAM. Offloading state to external tiers such as Redis \cite{redis_latency} prevents data loss, but incurs intrusive architectural refactoring and replaces nanosecond memory dereferences with network roundtrips.

Userspace checkpoint/restore via CRIU \cite{criu} provides an application-transparent alternative. In hypervisor literature, ``live migration'' classically refers to iterative pre-copy schemes \cite{clark2005} that track dirty pages via hardware MMU page tables, streaming memory while the virtual machine executes to achieve millisecond cutovers. In container environments lacking hardware virtualization traps, process-level live migration via CRIU and Kubernetes KEP-2008 \cite{reber2022} is operationally classified as \textit{decoupled snapshot-consistent live migration} (or warm snapshot migration) \cite{stoyanov2018, nadgowda2017, kubesnap, cedana2023, bellavista2021}. Here, migration denotes cross-node state transfer that preserves running process heaps and listening sockets without re-executing \texttt{main()} or rebuilding application memory structures, while honestly accepting a sub-second cutover blackout bounded by snapshot serialization and container runtime event loops.

This paper makes four empirical systems contributions:
\begin{itemize}
    \item \textbf{End-to-End Autonomous Controller:} We build a privileged DaemonSet operator (\texttt{PodLiveMigration} CRD) automating KEP-2008 checkpointing, Buildah OCI packaging, registry transfer, CRI-O restoration, and host-level Cilium eBPF routing across AWS EC2 nodes.
    \item \textbf{Statistical Rigor ($N = 36$ CRIU vs. $N = 20$ Cold Baseline):} We present a rigorous comparison between 36 CRIU migrations and 20 cold reschedules. A two-sided Mann-Whitney U test ($U = 252.5, p = 0.0660$) confirms that CRIU restoration does not impose a statistically significant cutover penalty over cold start at $\alpha = 0.05$. Post-restore tick regression ($r = 0.9624$) isolates true container unfreeze at $\approx 537$~ms, strongly supporting the hypothesis that cutover variance is dominated by Kubelet's 1~s PLEG relist cycle.
    \item \textbf{1~GB Heap Scaling, SHA-256 Verification \& Gzip Bottleneck:} We migrate dense numerical heaps up to 1024~MB with 100\% SHA-256 bit-level verification within 50.09~s (41.7\% of the Spot deadline), characterizing the Linux page-cache writeback cliff and proving that uncompressed Buildah packaging slashes 1~GB build time by 2.5$\times$ (from 34.02~s to 13.74~s).
    \item \textbf{In-Pod Sidecar vs. Host-Level eBPF Evaluation:} We empirically demonstrate why single-container KEP-2008 checkpointing severes loopback sockets in multi-container sidecar pods, and show how host-level Cilium eBPF routing preserves client connectivity without sidecar re-peering.
\end{itemize}

Because a restored pod receives a new Pod IP from the target node's CIDR (\texttt{10.244.2.0/24} $\to$ \texttt{10.244.1.0/24}), \texttt{/etc/criu/default.conf} specifies key flags \cite{criu}:
\begin{itemize}
    \item \texttt{tcp-close}: Restores listening sockets (\texttt{0.0.0.0:8090}) in the \texttt{LISTEN} state while closing established TCP sockets bound to the old Pod IP.
    \item \texttt{skip-in-flight}: Drops transient in-flight TCP handshakes occurring during 50~Hz probing at the instant of \texttt{ptrace} seizure.
    \item \texttt{skip-mnt /run/.containerenv}: Skips CRI-O's transient metadata mount so \texttt{CRImportCheckpoint} mount validation succeeds.
    \item \texttt{ext-unix-sk} and \texttt{shell-job}: Permits dumping external UNIX domain sockets and inherited stdio descriptors.
\end{itemize}

\subsection{Cutover Blackout Definition}
Our benchmark service uses \texttt{HTTP/1.0} behind a Kubernetes Service ClusterIP and Cilium L7 Envoy Ingress without long-hold request buffering. Between source pod deletion ($t_{\text{kill}}$) and target endpoint readiness ($t_4$), incoming requests fail immediately with connection refused or \texttt{HTTP 503}. We define cutover blackout $T_{\text{blackout}}$ strictly as the unavailability window during which probes fail, measured both by the operator clock ($t_4 - t_{\text{kill}}$) and by an external 50~Hz ($\pm 20$~ms) prober as the maximum interval between consecutive \texttt{HTTP 200 OK} responses.

\section{Latency, State Drift, and Evacuation Model}

\subsection{Stage Timestamps and Disruption Decomposition}
The operator records monotonic timestamps around each pipeline step: $t_0$ (pre-checkpoint), $t_1$ (post-dump), $t_2$ (post-build), $t_3$ (post-push), $t_{\text{kill}}$ (pre-delete probe $c_{\text{kill}}$ and pod deletion), and $t_4$ (first \texttt{HTTP 200 OK} from the restored pod):
\begin{align}
T_{\text{freeze}} &= t_1 - t_0, \quad T_{\text{build}} = t_2 - t_1, \quad T_{\text{push}} = t_3 - t_2 \\
T_{\text{restore}} &= t_4 - t_3, \quad T_{\text{blackout}} = t_4 - t_{\text{kill}} = T_{\text{restore}} - t_{\text{probe}}
\end{align}
where $t_{\text{probe}} = t_{\text{kill}} - t_3 \approx 1$--$2$~ms is pre-kill probe latency. Client-perceived disruption consists of source freeze stutter $T_{\text{freeze}}$ (threads paused by \texttt{ptrace}) plus cutover blackout $T_{\text{blackout}}$:
\begin{align}
T_{\text{disruption}} &= T_{\text{freeze}} + T_{\text{blackout}} \\
T_{\text{total}} &= T_{\text{freeze}} + T_{\text{build}} + T_{\text{push}} + T_{\text{restore}}
\end{align}

\subsection{State Drift (RPO), Post-Restore Ticks, and Rollback}
In \textbf{Mode A (Decoupled, \texttt{KeepRunning: true})}, CRI-O unfreezes the source container at $t_1$, allowing it to serve traffic while Buildah packages and pushes the image. State mutations occurring between the snapshot ($S_{\text{ckpt}} \approx c_{\text{dump}} + 1$) and pod deletion ($t_{\text{kill}}$) are lost upon cutover. At mutation rate $\lambda$, Recovery Point Objective (RPO) and lost updates $\Delta S_{\text{lost}}$ are:
\begin{align}
\text{RPO} &= T_{\text{build}} + T_{\text{push}} \\
\Delta S_{\text{lost}} &= c_{\text{kill}} - S_{\text{ckpt}} \approx \lambda \cdot (T_{\text{build}} + T_{\text{push}})
\label{eq:lost}
\end{align}
Workloads with external side effects require idempotency keys or write-ahead logging (WAL).

In \textbf{Mode B (Synchronous Stop-and-Copy, Analytical Projection)}, halting the source container at $t_1$ yields $\text{RPO} \equiv 0$, but extends service unavailability to the entire pipeline ($T_{\text{blackout}}^{\text{stop-and-copy}} = T_{\text{total}}$).

On the target node, \texttt{runc restore} unfreezes the process at $T_{\text{unfreeze}} < T_{\text{restore}}$, and the restored process immediately resumes incrementing from $S_{\text{ckpt}}$. However, the operator only probes $c_{\text{restore}}$ after Kubelet's PLEG loop (1~s period) updates \texttt{Pod.status.phase = Running} at $T_{\text{restore}} = T_{\text{unfreeze}} + \Delta t_{\text{pleg}}$:
\begin{equation}
c_{\text{restore}} - c_{\text{dump}} \approx \lambda \cdot (T_{\text{restore}} - T_{\text{unfreeze}})
\label{eq:post_restore}
\end{equation}

\subsection{Source-Side Spot Evacuation Condition}
When AWS issues a 120-second Spot Interruption Notice, only the source node is terminated at $t = 120$~s; target-side pull and restoration execute on the surviving destination node after $t_3$. Spot survival requires only that source evacuation $T_{\text{evac}}(M)$ complete within 120~s:
\begin{align}
T_{\text{evac}}(M) = &\ T_{\text{detect}} + T_{\text{freeze}}(M) \nonumber \\
&+ T_{\text{build}}(M) + T_{\text{push}}(M) < 120\text{ s}
\label{eq:spot_evac}
\end{align}
where $T_{\text{detect}} \approx 2.5$~s for a 5~s IMDSv2 poll interval.

Three crucial findings emerge:
\begin{enumerate}
    \item \textbf{Statistical Equivalence of Cutover Latency:} Median cutover blackout is 1064.5~ms for CRIU versus 1019.0~ms for cold startup (+45.5~ms, +4.5\%). While the mean difference is 125.4~ms ($1132.4 \pm 241.1$~ms vs. $1007.0 \pm 231.2$~ms), a two-sided Mann-Whitney U test confirms that the difference between the distributions is \textbf{not statistically significant} at $\alpha = 0.05$ ($U = 252.5, z = -1.84, p = 0.0660$; Welch's $t(43.8) = 1.91, p = 0.0628$, 95\% CI $[-3.0, +253.7]$~ms). Restoring the 5.16~MiB checkpoint image via CRIU incurs no detectable latency penalty over cold start, while preserving 100\% of the heap.
    \item \textbf{Kubelet PLEG Synchronization Dominance:} Both CRIU restore ($\sigma = 241.1$~ms) and cold restart ($\sigma = 231.2$~ms) standard deviations are roughly consistent with a uniform 1~s Kubelet PLEG relist cycle ($1000 / \sqrt{12} \approx 288.7$~ms). The operator polls pod status every 50~ms, well below observed variance. Linear regression of post-restore tick accumulation $(c_{\text{restore}} - c_{\text{dump}})$ against $T_{\text{restore}}$ across all 36 runs yields $r = 0.9624$, slope $\hat{\lambda} = 9.96$~ticks/s (matching the 10.0~Hz counter), and x-intercept $T_{\text{unfreeze}} = 537.1$~ms. This strongly supports the hypothesis that CRI-O unfreezes the container in $\approx 537$~ms, whereas the remaining 261--1151~ms of blackout is Kubelet PLEG relist quantization delay ($\Delta t_{\text{pleg}}$).
    \item \textbf{Trace \#35 vs. Trace \#36 State Dynamics:} In Trace \#35 ($51 \to 60 \to 57, T_{\text{restore}} = 1080$~ms), the restored container ticked 5 times during its 543~ms PLEG synchronization delay ($1080 - 537$~ms), whereas in Trace \#36 ($77 \to 85 \to 79, T_{\text{restore}} = 798$~ms), a short 261~ms PLEG delay yielded only 1 post-restore tick.
\end{enumerate}

Three systems insights emerge:
\begin{enumerate}
    \item \textbf{Bit-Exact Restoration within Spot SLA:} All heaps up to 1024~MB restored with 100\% SHA-256 bit-level integrity. At 1~GB, source evacuation took 50.09~s (41.7\% of the 120~s Spot SLA), confirming that 1--2~GB workloads can be safely evacuated before preemption.
    \item \textbf{Kernel Dirty-Page Writeback Throttling in $T_{\text{freeze}}$:} From 26~MB to 512~MB, $T_{\text{freeze}}$ remains sub-second (144~ms $\to$ 760~ms, effective write rate $\approx 680$~MiB/s) because writes are absorbed into the Linux page cache. On our 8~GB worker nodes (\texttt{vm.dirty\_background\_ratio = 10}, \texttt{vm.dirty\_ratio = 20}), background flushing starts at $\approx 778$~MB, while synchronous throttling in \texttt{balance\_dirty\_pages()} engages at $\approx 1555$~MB or when dirty page rate overwhelms storage. Dumping a 1024~MB checkpoint archive pushes dirty page accumulation past background limits and saturates EBS \texttt{gp3} bandwidth ($\approx 138$~MiB/s), forcing synchronous I/O throttling and jumping $T_{\text{freeze}}$ by $9.8\times$ to 7.464~s.
    \item \textbf{Gzip Incompressibility and \texttt{--disable-compression} Speedup:} Incompressible floating-point weights produce OCI layers matching the heap size. Under default Buildah single-threaded \texttt{gzip}, $T_{\text{build}}$ consumes 32.060~s at 1~GB ($64.0\%$ of evacuation time). Passing \texttt{--disable-compression} (\texttt{-D}) bypasses gzip serialization, slashing 1~GB packaging to \textbf{13.743~s} (a 2.3$\times$ speedup, saving 20.28~s) and 256~MB packaging from 5.796~s to \textbf{1.473~s} (3.9$\times$ speedup). The steep jump between 128~MB and 256~MB under gzip reflects L3 cache eviction (8~MB per core) and dynamic layer buffer reallocation. For cluster-local registries, disabling compression is the optimal configuration.
\end{enumerate}

\subsection{Experiment 3: In-Pod Sidecar Proxy vs. Host-Level eBPF}
To evaluate service-mesh architectures, we deployed a two-container pod (\texttt{bench-sidecar-pod}) on \texttt{k8s-worker-1}: \texttt{stream-server} listening on \texttt{127.0.0.1:8090} and an \texttt{envoy-sidecar} proxy on \texttt{0.0.0.0:15006} forwarding over a persistent loopback TCP connection. Prior to migration, probes to \texttt{:15006} returned \texttt{HTTP 200 OK} (\texttt{ram\_counter = 505}).

When triggered via \texttt{PodLiveMigration}, KEP-2008 checkpointed \texttt{stream-server} in 118~ms, and CRI-O restored the container on \texttt{k8s-worker-2}. However, because KEP-2008 operates at \textit{single-container granularity} rather than pod-level granularity, and CRIU's \texttt{tcp-close} option closes established sockets, the restored application was isolated from the co-scheduled sidecar ($T_{\text{blackout}} = \infty$, timing out at 120~s). Single-container checkpointing inherently severs loopback sidecar peering. By contrast, host-level Cilium eBPF routing decouples L4/L7 service redirection from the pod network namespace lifecycle, enabling seamless stateful container live migration without sidecar re-peering.

\section{Related Work}
Virtual machine live migration was pioneered by Clark et al. \cite{clark2005} via iterative pre-copy. In container ecosystems, early systems such as Voyager \cite{nadgowda2017} and work by Stoyanov and Kollingbaum \cite{stoyanov2018} coordinated CRIU memory checkpoints with layered union filesystems. Reber \cite{reber2022} standardized the Kubelet Checkpoint API (KEP-2008) in Kubernetes v1.25+ for forensic debugging.

Recent efforts (2021--2025) focus on operational container live migration: KubeSnap \cite{kubesnap} optimized checkpoint streaming, and Cedana \cite{cedana2023} commercialized stateful container migration for GPU and Spot instances. In edge computing, Bellavista et al. \cite{bellavista2021}, Puliafito et al. \cite{puliafito2021}, and Wang et al. \cite{wang2022} surveyed and evaluated stateful container mobility across heterogeneous edge clusters. Modern eBPF datapaths \cite{cilium} demonstrate how sidecar-free host-level routing overcomes pod-namespace lifecycle limitations, complementing our findings.

\section{Limitations and Future Work}
Our workload employs \texttt{HTTP/1.0} with CRIU's \texttt{tcp-close} flag; preserving persistent \texttt{HTTP/1.1} keep-alive, WebSocket, or gRPC streams requires ingress request buffering or CRIU \texttt{--tcp-established} coupled with BGP/eBPF virtual IP migration. Second, while disabling Buildah compression reduces packaging time, multi-gigabyte heaps would benefit from direct \texttt{criu page-server} streaming and memory pre-dumping (\texttt{criu dump --pre-dump}) to achieve sub-second preemption bounds.

\section{Conclusion}
We presented an empirical study of snapshot-consistent container live migration in Kubernetes using CRI-O, CRIU v4.3, Buildah, and host-level Cilium eBPF routing. Across $N = 36$ live migrations and $N = 20$ cold reschedules on AWS EC2, CRIU cutover blackout (median 1064.5~ms) exhibits no statistically significant difference from native cold restart ($p = 0.0660$) while preserving 100\% of heap state up to 1~GB within Spot deadlines. Disabling Buildah compression slashes 1~GB packaging by 2.3$\times$, while host-level eBPF avoids the architectural failure of in-pod sidecars under single-container checkpointing.
