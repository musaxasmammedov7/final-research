\begin{abstract}
Stateful singleton containers lacking distributed replication lose volatile heap state during Kubernetes node maintenance and cloud Spot instance preemptions. We evaluate an automated, snapshot-consistent pod migration pipeline coordinating CRIU (v4.3), the Kubelet Checkpoint API (KEP-2008), Buildah OCI packaging, CRI-O (v1.31), and Cilium eBPF routing across AWS EC2 nodes. Across 36 migrations of a stateful service compared against 20 cold reschedules, decoupled migration achieves a median cutover blackout of 1064.5~ms versus 1019.0~ms for cold restart (+4.5\% overhead) while preserving heap state. A Mann-Whitney U test ($p = 0.0660$) detects no statistically significant cutover difference, with variance governed by Kubelet's 1~s PLEG cycle. Decoupled migration incurs bounded state drift of 669.0~ms, whereas stop-and-copy yields zero drift at the cost of extending blackout to 1.88~s. Scaling heaps to 1024~MB (1~GB) confirms 100\% bit-exact SHA-256 integrity within 55.09~s worst-case source evacuation (45.9\% of the 120~s Spot deadline), where uncompressed Buildah packaging slashes build time from 32.06~s to 13.74~s (reducing evacuation to 36.78~s). While 1~GB migration cutover is comparable to estimated cold state reconstruction from cloud storage (11--30~s), checkpointing eliminates application-level persistence tiers, with cutover becoming advantageous over cold rebuild from $\approx 256$~MB (2.1~s vs. 3.5--7.5~s). Finally, single-container KEP-2008 checkpointing severs in-pod loopback sockets, suggesting node-level routing as a less fragile alternative.
\end{abstract}

\section{Introduction}
Kubernetes manages workloads under the foundational assumption that container instances are ephemeral and stateless \cite{burns2016borg}. When worker nodes undergo kernel maintenance (\texttt{kubectl drain}) or cloud virtual machines are reclaimed, stateless microservices maintain availability by spinning up replacement replicas before terminating old instances (\texttt{maxSurge}).

However, critical production classes maintain large, mutable in-memory heaps without built-in distributed consensus:
\begin{enumerate}
    \item \textbf{Scientific \& Numerical Solvers:} Iterative physics simulations, linear algebra solvers, and legacy C++/Python runtimes accumulating state over hours.
    \item \textbf{Warm ML Inference Caches \& Aggregators:} High-dimensional embedding buffers, key-value transformer caches, and session aggregators where rebuilding state from cold storage imposes severe warm-up latency.
\end{enumerate}

Deploying these workloads on Amazon Web Services (AWS) EC2 Spot instances yields 70--90\% compute cost savings, but subjects pods to abrupt reclamation with a 120-second termination notice \cite{netflix_spot, aws_spot}. Standard eviction issues \texttt{SIGTERM} followed by \texttt{SIGKILL}, destroying volatile RAM. Offloading state to external tiers such as Redis \cite{redis_latency} prevents data loss, but incurs intrusive architectural refactoring and replaces nanosecond memory dereferences with network roundtrips.

Userspace checkpoint/restore via CRIU \cite{criu} provides an application-transparent alternative. In hypervisor literature, ``live migration'' classically refers to iterative pre-copy schemes \cite{clark2005} that track dirty pages via hardware MMU page tables, streaming memory while the virtual machine executes to achieve millisecond cutovers. In container environments lacking hardware virtualization traps, process-level live migration via CRIU and Kubernetes KEP-2008 \cite{reber2022} is operationally distinct. In this paper, we use the term \textit{checkpoint/restore-based container migration} to denote cross-node state transfer that preserves running process heaps and listening sockets without re-executing \texttt{main()} or rebuilding application memory structures, while accepting a sub-second cutover blackout bounded by snapshot serialization and container runtime event loops.

This paper makes four empirical systems contributions:
\begin{itemize}
    \item \textbf{End-to-End Autonomous Controller:} We build a privileged DaemonSet operator (\texttt{PodLiveMigration} CRD) automating KEP-2008 checkpointing, Buildah OCI packaging, registry transfer, CRI-O restoration, and host-level Cilium eBPF routing across AWS EC2 nodes.
    \item \textbf{Statistical Evaluation ($N = 36$ CRIU vs. $N = 20$ Cold Baseline):} Comparing 36 CRIU migrations against 20 cold reschedules, a two-sided Mann-Whitney U test ($U = 252.5, p = 0.0660$) shows no statistically significant cutover difference at $\alpha = 0.05$, though the 95\% CI ($[-6.7, +257.4]$~ms) does not rule out overheads up to $\approx 25\%$. Tick regression ($r = 0.9624$) isolates true container unfreeze at $\approx 537$~ms, showing that variance is dominated by Kubelet's 1~s PLEG relist cycle.
    \item \textbf{1~GB Heap Scaling, SHA-256 Verification \& Packaging Optimization:} We migrate dense numerical heaps up to 1024~MB with 100\% SHA-256 bit-level verification within 55.09~s worst-case source evacuation (45.9\% of the 120~s Spot SLA), characterizing Linux page-cache writeback behavior and demonstrating that uncompressed Buildah packaging slashes 1~GB build time from 32.06~s to 13.74~s (reducing evacuation time to 36.78~s, or 30.6\% of SLA).
    \item \textbf{State Reconstruction Benefit \& Sidecar Case Study:} We contrast the recovery advantage of checkpointing against estimated cold state reconstruction (11--30~s for 1~GB), and analyze the architectural constraints of single-container KEP-2008 checkpointing under in-pod sidecar proxies, suggesting node-level routing as a less fragile architecture.
\end{itemize}

Because a restored pod receives a new Pod IP from the target node's CIDR (\texttt{10.244.2.0/24} $\to$ \texttt{10.244.1.0/24}), \texttt{/etc/criu/default.conf} specifies key flags \cite{criu}:
\begin{itemize}
    \item \texttt{tcp-close}: Restores listening sockets (\texttt{0.0.0.0:8090}) in the \texttt{LISTEN} state while closing established TCP sockets bound to the old Pod IP.
    \item \texttt{skip-in-flight}: Drops transient in-flight TCP handshakes occurring during 50~Hz probing at the instant of \texttt{ptrace} seizure.
    \item \texttt{skip-mnt /run/.containerenv}: Skips CRI-O's transient metadata mount so \texttt{CRImportCheckpoint} mount validation succeeds.
    \item \texttt{ext-unix-sk} and \texttt{shell-job}: Permits dumping external UNIX domain sockets and inherited stdio descriptors.
\end{itemize}

\subsection{Cutover Blackout Definition}
Our benchmark service uses \texttt{HTTP/1.0} behind a Kubernetes Service ClusterIP and Cilium L7 Envoy Ingress without long-hold request buffering. Between source pod deletion ($t_{\text{kill}}$) and target endpoint readiness ($t_4$), incoming requests fail immediately with connection refused or \texttt{HTTP 503}. We define cutover blackout $T_{\text{blackout}}$ strictly as the unavailability window during which probes fail, measured both by the operator clock ($t_4 - t_{\text{kill}}$) and by an external 50~Hz ($\pm 20$~ms) prober as the maximum interval between consecutive \texttt{HTTP 200 OK} responses.

\section{Latency, State Drift, and Evacuation Model}

\subsection{Stage Timestamps and Disruption Decomposition}
The operator records monotonic timestamps around each pipeline step: $t_0$ (pre-checkpoint), $t_1$ (post-dump), $t_2$ (post-build), $t_3$ (post-push), $t_{\text{kill}}$ (pre-delete probe $c_{\text{kill}}$ and pod deletion), and $t_4$ (first \texttt{HTTP 200 OK} from the restored pod):
\begin{align}
T_{\text{freeze}} &= t_1 - t_0, \quad T_{\text{build}} = t_2 - t_1, \quad T_{\text{push}} = t_3 - t_2 \\
T_{\text{restore}} &= t_4 - t_3, \quad T_{\text{blackout}} = t_4 - t_{\text{kill}} = T_{\text{restore}} - t_{\text{probe}}
\end{align}
where $t_{\text{probe}} = t_{\text{kill}} - t_3 \approx 1$--$2$~ms is pre-kill probe latency. Client-perceived disruption consists of source freeze stutter $T_{\text{freeze}}$ (threads paused by \texttt{ptrace}) plus cutover blackout $T_{\text{blackout}}$:
\begin{align}
T_{\text{disruption}} &= T_{\text{freeze}} + T_{\text{blackout}} \\
T_{\text{total}} &= T_{\text{freeze}} + T_{\text{build}} + T_{\text{push}} + T_{\text{restore}}
\end{align}

\subsection{State Drift (RPO), Post-Restore Ticks, and Rollback}
In \textbf{Mode A (Decoupled, \texttt{KeepRunning: true})}, CRI-O unfreezes the source container at $t_1$, allowing it to serve traffic while Buildah packages and pushes the image. State mutations occurring between the snapshot ($S_{\text{ckpt}} \approx c_{\text{dump}} + 1$) and pod deletion ($t_{\text{kill}}$) are lost upon cutover. At mutation rate $\lambda$, Recovery Point Objective (RPO) and lost updates $\Delta S_{\text{lost}}$ are:
\begin{align}
\text{RPO} &= T_{\text{build}} + T_{\text{push}} \\
\Delta S_{\text{lost}} &= c_{\text{kill}} - S_{\text{ckpt}} \approx \lambda \cdot (T_{\text{build}} + T_{\text{push}})
\label{eq:lost}
\end{align}
Workloads with external side effects require idempotency keys or write-ahead logging (WAL).

In \textbf{Mode B (Synchronous Stop-and-Copy, Analytical Projection)}, halting the source container at $t_1$ yields $\text{RPO} \equiv 0$, but extends service unavailability to the entire pipeline ($T_{\text{blackout}}^{\text{stop-and-copy}} = T_{\text{total}}$).

On the target node, \texttt{runc restore} unfreezes the process at $T_{\text{unfreeze}} < T_{\text{restore}}$, and the restored process immediately resumes incrementing from $S_{\text{ckpt}}$. However, the operator only probes $c_{\text{restore}}$ after Kubelet's PLEG loop (1~s period) updates \texttt{Pod.status.phase = Running} at $T_{\text{restore}} = T_{\text{unfreeze}} + \Delta t_{\text{pleg}}$:
\begin{equation}
c_{\text{restore}} - c_{\text{dump}} \approx \lambda \cdot (T_{\text{restore}} - T_{\text{unfreeze}})
\label{eq:post_restore}
\end{equation}

\subsection{Source-Side Spot Evacuation Condition}
When AWS issues a 120-second Spot Interruption Notice, only the source node is terminated at $t = 120$~s; target-side pull and restoration execute on the surviving destination node after $t_3$. Spot survival requires only that worst-case source evacuation $T_{\text{evac}}^{\text{worst}}(M)$ complete within 120~s:
\begin{align}
T_{\text{evac}}^{\text{worst}}(M) = &\ T_{\text{detect}}^{\text{worst}} + T_{\text{freeze}}(M) \nonumber \\
&+ T_{\text{build}}(M) + T_{\text{push}}(M) < 120\text{ s}
\label{eq:spot_evac}
\end{align}
where $T_{\text{detect}}^{\text{worst}} = 5.0$~s accounts for the worst-case detection latency under a 5~s IMDSv2 polling period.

Three crucial findings emerge:
\begin{enumerate}
    \item \textbf{Cutover Latency Comparison (No Statistically Significant Difference at $\alpha = 0.05$):} Median cutover blackout is 1064.5~ms for CRIU versus 1019.0~ms for cold startup (+45.5~ms, +4.5\%). While sample means differ by 125.4~ms ($1132.4 \pm 241.1$~ms vs. $1007.0 \pm 231.2$~ms), a two-sided Mann-Whitney U test confirms that this difference is \textbf{not statistically significant} at $\alpha = 0.05$ ($U = 252.5, z = -1.84, p = 0.0660$; Welch's $t(40.8) = 1.91, p = 0.0628$). Although the 95\% confidence interval of $[-6.7, +257.4]$~ms does not rule out minor latency overheads under larger sample sizes, it does not provide evidence of a large cutover penalty over cold pod initialization.
    \item \textbf{Kubelet PLEG Synchronization Dominance:} Both CRIU restore ($\sigma = 241.1$~ms) and cold restart ($\sigma = 231.2$~ms) standard deviations are roughly consistent with a uniform 1~s Kubelet PLEG relist cycle ($1000 / \sqrt{12} \approx 288.7$~ms). The operator polls pod status every 50~ms, well below observed variance. Linear regression of post-restore tick accumulation $(c_{\text{restore}} - c_{\text{dump}})$ against $T_{\text{restore}}$ across all 36 runs yields $r = 0.9624$, slope $\hat{\lambda} = 9.96$~ticks/s (matching the 10.0~Hz counter), and x-intercept $T_{\text{unfreeze}} = 537.1$~ms. This strongly supports the hypothesis that CRI-O unfreezes the container in $\approx 537$~ms, whereas the remaining 261--1151~ms of blackout is Kubelet PLEG relist quantization delay ($\Delta t_{\text{pleg}}$).
    \item \textbf{Trace \#35 vs. Trace \#36 State Dynamics:} In Trace \#35 ($51 \to 60 \to 57, T_{\text{restore}} = 1080$~ms), the restored container ticked 5 times during its 543~ms PLEG synchronization delay ($1080 - 537$~ms), whereas in Trace \#36 ($77 \to 85 \to 79, T_{\text{restore}} = 798$~ms), a short 261~ms PLEG delay yielded only 1 post-restore tick.
\end{enumerate}

Three systems insights emerge:
\begin{enumerate}
    \item \textbf{Bit-Exact Restoration within Spot SLA:} All heaps up to 1024~MB restored with 100\% SHA-256 bit-level integrity. Under worst-case Spot detection ($T_{\text{detect}}^{\text{worst}} = 5.0$~s) and default gzip, total source evacuation took 55.09~s (45.9\% of the 120~s Spot SLA), confirming that 1--2~GB workloads can be safely evacuated before preemption.
    \item \textbf{Kernel Dirty-Page Writeback in $T_{\text{freeze}}$:} From 26~MB to 512~MB, $T_{\text{freeze}}$ remains sub-second (144~ms $\to$ 760~ms) as writes are absorbed in RAM cache. At 1~GB, \texttt{/proc/meminfo} shows uncommitted dirty memory hitting 783.6~MB (\texttt{vm.dirty\_background\_ratio = 10}), triggering flusher threads to serialize writes to EBS \texttt{gp3}. This transition is consistent with dirty-page writeback serialization when memory pressure forces synchronous disk flushing of \texttt{checkpoint.tar}, bounding $T_{\text{freeze}}$ by EBS write bandwidth ($\approx 124$--$138$~MB/s).
    \item \textbf{Gzip Incompressibility and \texttt{--disable-compression} Speedup:} Incompressible floating-point weights produce OCI layers matching the heap size. Under default Buildah single-threaded \texttt{gzip}, $T_{\text{build}}$ consumes 32.060~s at 1~GB. Passing \texttt{--disable-compression} (\texttt{-D}) bypasses gzip serialization, slashing 1~GB packaging to \textbf{13.743~s} (a 2.3$\times$ speedup, saving 18.32~s) and reducing worst-case evacuation from 55.09~s to \textbf{36.78~s} (30.6\% of Spot budget). For cluster-local registries over local VPC links (where 1029~MiB pulls in 8.5~s, matching the $\approx 1$~Gbps baseline network tier), disabling compression is optimal.
\end{enumerate}

\subsection{Why Migrate? Checkpoint Restoration vs. Cold State Rebuild}
A standard cold reschedule launches an empty container in $\approx 1.0$~s, but resets in-memory application state to zero. For stateful workloads, the replacement pod must reconstruct its state from external storage before serving traffic. As an analytical estimate, downloading a 1~GB snapshot from cloud object storage (Amazon S3) over assumed multi-tenant bandwidth (300--800~Mbps) requires 10.2--27.3~s transfer plus 1.05--2.5~s deserialization, yielding an estimated recovery window of \textbf{11.2--29.8~s} (or minutes if recomputed).

At 1~GB, migration cutover ($T_{\text{restore}} = 17.328$~s) is comparable to this cold reconstruction estimate, with 24.3~s state drift (RPO) and 36.8~s worst-case evacuation (full pipeline $T_{\text{freeze}} + T_{\text{build}} + T_{\text{push}} + T_{\text{restore}} \approx 49.1$~s). The architectural advantage for 1~GB workloads is eliminating external persistence tiers and application-level serialization. For smaller heaps, cutover is comparable at 64--128~MB (0.95--1.70~s vs. estimated 0.6--3.4~s download) and advantageous from $\approx 256$~MB (2.10~s vs. 3.5--7.5~s).

Profiled from target CRI-O daemon timestamps (\texttt{journalctl -u crio}) and Kubelet runtime events, target restoration decomposes into four distinct latency phases: (1) layer pull over the VPC network ($\approx 8.5$~s, matching $\approx 1$~Gbps baseline bandwidth), (2) CRI-O container storage extraction ($\approx 4.8$~s), (3) \texttt{runc/criu restore} virtual memory mapping and process unfreezing ($\approx 3.2$~s), and (4) Kubelet PLEG status synchronization ($\approx 0.8$~s). Network transfer and disk unpacking account for over 76\% of restoration latency.

\subsection{Architectural Limitations of Single-Container Checkpointing with In-Pod Sidecars}
To evaluate service meshes, we deployed a two-container pod (\texttt{bench-sidecar-pod}) on \texttt{k8s-worker-1} with \texttt{stream-server} (:8090) and an \texttt{envoy-sidecar} proxy (:15006) forwarding over loopback TCP. KEP-2008 checkpointed \texttt{stream-server} in 118~ms, and CRI-O restored it on \texttt{k8s-worker-2}. However, because KEP-2008 operates at single-container granularity and CRIU's \texttt{tcp-close} closes sockets, the restored application was isolated from the co-scheduled sidecar ($T_{\text{blackout}} = \infty$, timing out at 120~s). Single-container checkpointing inherently severs loopback peering; node-level routing (e.g., Cilium eBPF host-routing) decouples service redirection from pod network namespaces, offering a more robust design.

\section{Related Work}
Clark et al. \cite{clark2005} established VM live migration via iterative pre-copy. Voyager \cite{nadgowda2017} and Stoyanov and Kollingbaum \cite{stoyanov2018} combined CRIU checkpoints with layered filesystems for containers. Reber \cite{reber2022} standardized the Kubelet Checkpoint API (KEP-2008) in Kubernetes v1.25+.
Recent work (2024--2025) addresses operational container migration: Zhang et al. \cite{kubespt2025} introduced KubeSPT for stateful pod teleportation; Calagna et al. \cite{calagna2024} modeled robust stateful edge microservice migration; Bellavista et al. \cite{bellavista2024} evaluated Kubernetes-enhanced ML migration; and Poggiani et al. \cite{poggiani2024} investigated multi-cluster live migration of multi-container pods across edge systems by combining Liqo multi-cluster federation with CRI-O and CRIU. Our work provides a complementary single-cluster empirical study: rather than designing multi-cluster federation, we quantify upstream KEP-2008 and CRI-O runtime bottlenecks, including Kubelet PLEG quantization, Linux dirty-page writeback saturation, and Buildah compression scaling up to 1~GB heaps.

\section{Limitations and Future Work}
Our workload employs \texttt{HTTP/1.0} with CRIU's \texttt{tcp-close}; persistent \texttt{HTTP/1.1}, WebSocket, or gRPC connections require ingress request buffering or CRIU \texttt{--tcp-established}. Multi-gigabyte heaps would benefit from direct \texttt{criu page-server} streaming and pre-dumping to achieve sub-second preemption. Finally, our multi-size heap scaling is an exploratory single run per size; systematic multi-trial profiling with fine-grained step intervals is needed to map the exact writeback saturation curve.

\section{Conclusion}
We presented an empirical study of checkpoint/restore-based pod migration in Kubernetes using CRI-O, CRIU v4.3, Buildah, and Cilium eBPF routing. Across $N = 36$ migrations and $N = 20$ cold reschedules on AWS EC2, we detected no statistically significant difference in median cutover latency ($p = 0.0660, 95\%\text{ CI } [-6.7, +257.4]$~ms), while preserving 100\% of heap state up to 1~GB within Spot deadlines. While 1~GB migration cutover ($T_{\text{restore}} = 17.3$~s) is comparable to estimated cold cloud storage reconstruction (11--30~s), checkpointing eliminates external persistence tiers and serialization logic, with cutover becoming advantageous over cold rebuild from $\approx 256$~MB (2.10~s vs. estimated 3.5--7.5~s). Disabling Buildah compression slashes 1~GB packaging from 32.06~s to 13.74~s (saving 18.32~s). Finally, single-container checkpointing severs loopback sidecars, favoring node-level routing.
