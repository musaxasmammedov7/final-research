\begin{abstract}
While stateless microservices in Kubernetes achieve high availability through multi-replica deployments, rolling updates, and PodDisruptionBudgets, stateful singleton workloads---such as active session brokers, in-memory stream processors, and stateful caching nodes---cannot be trivially replicated without substantial distributed consensus overhead or intrusive application refactoring. When cluster nodes undergo maintenance or ephemeral cloud infrastructure (e.g., Amazon Web Services EC2 Spot instances) is reclaimed via a two-minute preemption notification, the standard Kubernetes scheduler executes a graceful teardown (\texttt{SIGTERM} followed by \texttt{SIGKILL}), destroying all volatile in-memory heap state.

This paper designs, implements, and evaluates a snapshot-consistent live migration architecture for stateful Kubernetes workloads. The pipeline coordinates the Linux Checkpoint/Restore in Userspace subsystem (CRIU v3.16.1) via the Kubelet Checkpoint API (KEP-2008), OCI artifact packaging via Buildah, the CRI-O container runtime (v1.31), and a sidecar-free Cilium eBPF Ingress architecture. We systematically evaluate the engineering trade-off between client-observed cutover blackout (Recovery Time Objective, RTO) and snapshot state drift (Recovery Point Objective, RPO). 

Under a continuous 50~Hz ($\pm 20$~ms) probing evaluation on AWS EC2, the decoupled migration pipeline achieves a cutover blackout window of 797--1078~ms (a 16.4\%--38.2\% reduction compared to native cold reschedule at 1289~ms). When accounting for the initial memory serialization freeze stutter ($T_{\text{freeze}} \approx 147$--$159$~ms), cumulative client-perceived disruption spans 944--1237~ms (a 4.0\%--26.8\% improvement over cold restart). We document an empirical state drift of $\approx 696$~ms ($\Delta S = 6$ uncommitted updates under a 10~Hz tick rate), analyze the risks of observable time rollback in transactional applications, evaluate memory scaling limits relative to the AWS Spot 120-second preemption deadline, and release our implementation as open-source.
\end{abstract}

Kubernetes, Container Live Migration, CRIU, CRI-O, Cilium eBPF, Stateful Workloads, Spot Instances, Recovery Point Objective.

\section{Introduction}
Container orchestration platforms, led by Kubernetes, rely on the premise of microservice idempotency and disposable instances \cite{burns2016borg}. In stateless deployments, node drain operations (\texttt{kubectl drain}) and instance preemptions are handled transparently: the control plane provisions replacement pods prior to terminating old replicas via rolling update strategies.

However, an important class of cloud-native workloads relies on long-running, in-memory volatile state:
\begin{enumerate}
    \item \textbf{In-Memory Session Brokers and State Engines:} Streaming analytics engines (e.g., Apache Flink task slots), distributed game session coordinators, and caching nodes maintain gigabytes of volatile heap allocations.
    \item \textbf{Real-Time Inference and Aggregation Pipelines:} Sensor ingest pipelines and windowed aggregators retain state in volatile memory to avoid database round-trip serialization.
\end{enumerate}

When these stateful singleton workloads run on ephemeral cloud instances---most notably Amazon Web Services (AWS) EC2 Spot instances, which offer 70--90\% cost reductions relative to On-Demand pricing but are subject to preemption with a strict 120-second notice \cite{netflix_spot, aws_spot}---standard eviction results in complete state loss. When a node is drained, the kubelet issues a \texttt{SIGTERM} signal; upon expiration of \texttt{terminationGracePeriodSeconds} (or immediately upon Spot preemption deadlines), a \texttt{SIGKILL} signal destroys the address space, resetting the application to pristine zero state.

Historically, engineering teams prevent state loss by offloading volatile variables to distributed key-value storage (e.g., Redis clusters) \cite{redis_latency}. While viable, this paradigm introduces three critical trade-offs: (i) serialization and network latency overheads (hundreds of microseconds across nodes compared to $\approx 100$~ns for local L3 CPU cache/memory bus); (ii) complex application-level refactoring of existing monolithic and legacy binaries; and (iii) substantial infrastructure overhead for high-availability database clustering.

To avoid application refactoring while supporting infrastructure mobility, container live migration has emerged as an attractive alternative \cite{stoyanov2018, nadgowda2017}. In this paper, we explore the integration of checkpoint-restore mechanisms natively within Kubernetes. Our primary contributions are:
\begin{itemize}
    \item \textbf{Decoupled Migration Architecture:} We design an automated 9-step orchestration pipeline combining KEP-2008 checkpointing \cite{reber2022}, CRI-O, and Buildah to migrate containers across AWS EC2 physical instances without application modifications.
    \item \textbf{Formalization of RTO vs. RPO Trade-offs:} We demonstrate that decoupling memory dumping from pod deletion minimizes client-observed cutover downtime ($T_{\text{blackout}} \in [797, 1078]$~ms), but introduces a bounded state drift ($\text{RPO} \approx 696$~ms), formalizing the distinction between freeze latency, cutover blackout, and cumulative disruption.
    \item \textbf{Analysis of Service Mesh Topologies:} We evaluate how sidecar-free eBPF architectures (Cilium) resolve CRIU socket serialization crashes caused by in-pod loopback proxies in traditional sidecar meshes.
    \item \textbf{Scalability and Spot Feasibility Modeling:} We model multi-stage migration latency across heap capacities ($26$~MB to $8$~GB) relative to the AWS 120-second termination window and analyze memory scaling bottlenecks.
\end{itemize}

\subsection{Ingress Routing vs. L4 Socket Boundaries}
When a pod migrates from \texttt{k8s-worker-1} to \texttt{k8s-worker-2}, its Pod IP changes (e.g., from \texttt{10.0.1.45} to \texttt{10.0.2.112}). If external clients connected directly to the Pod IP via plain L4 TCP, the 4-tuple (\textit{src\_ip, src\_port, dst\_ip, dst\_port}) would be invalidated, triggering kernel \texttt{RST} packets.

Our architecture routes external traffic through an L7 Ingress Gateway (Cilium Ingress / Envoy). The ingress proxy terminates external client TCP/HTTP sessions. During migration:
\begin{itemize}
    \item External client connections remain established at the ingress proxy.
    \item During the cutover blackout window ($T_{\text{blackout}}$), incoming requests are queued or retried by Envoy (configured with 3 retries on connect failure with a 25~ms backoff).
    \item As soon as the target pod completes CRI-O restore and passes readiness probes, Cilium's eBPF datapath updates the ingress endpoint table, directing buffered traffic to the new Pod IP.
\end{itemize}

\subsection{Service Mesh Topologies: Sidecar vs. Sidecar-Free}
In traditional service mesh architectures (e.g., Istio), an Envoy proxy runs as a sidecar container inside the application pod namespace. Traffic is intercepted via \texttt{iptables PREROUTING} rules over the \texttt{127.0.0.1} loopback interface.

When CRIU attempts to checkpoint a pod containing an active Envoy sidecar, two failure modes arise:
\begin{enumerate}
    \item \textbf{Loopback Socket Entanglement:} CRIU cannot serialize active TCP connections bound to \texttt{127.0.0.1} when the remote target host cannot guarantee identical socket descriptors and peer namespaces.
    \item \textbf{Namespace-Locked Routing State:} Pod-level \texttt{iptables} NAT state and inter-container UNIX domain sockets cannot be serialized and restored independently of the application process.
\end{enumerate}

A \textit{sidecar-free} topology (Cilium eBPF Service Mesh) \cite{cilium} mitigates this issue by hosting Envoy at the node level. eBPF socket programs hook into socket events at the host cgroup boundary, avoiding namespace-locked proxies. Consequently, the application pod namespace contains only the isolated target process, enabling clean CRIU serialization.

\section{Mathematical Latency, Drift, and Scalability Model}

\subsection{Latency Decomposition: Disruption vs. Blackout}
Client-observed service disruption during migration consists of two distinct phases:
\begin{equation}
T_{\text{disruption}} = T_{\text{freeze}} + T_{\text{blackout}}
\end{equation}
\begin{itemize}
    \item \textbf{Freeze Stutter ($T_{\text{freeze}}$):} During $T_{\text{dump}}$, CRIU attaches to the process via \texttt{PTRACE\_SEIZE} and halts thread execution while dumping memory pages from \texttt{/proc/PID/pagemap}. Client requests arriving during this window are queued in TCP socket buffers, experiencing a transient latency spike.
    \item \textbf{Cutover Blackout ($T_{\text{blackout}}$):} The elapsed time between source pod termination ($t_{\text{kill}}$) and verified successful response from the target pod ($t_{\text{ready}}$):
    \begin{equation}
    T_{\text{blackout}} = t_{\text{ready}} - t_{\text{kill}} = T_{\text{restore}} + T_{\text{route\_sync}} \pm \delta_{\text{probe}}
    \end{equation}
    where $\delta_{\text{probe}} = 20$~ms represents the sampling discretization of the 50~Hz probing harness.
\end{itemize}
The total end-to-end orchestration duration is:
\begin{equation}
T_{\text{total}} = T_{\text{dump}} + T_{\text{build}} + T_{\text{push}} + T_{\text{restore}}
\end{equation}

\subsection{The RTO vs. RPO Trade-off}
The migration orchestrator can operate in two distinct modes:

\subsubsection{Mode A: Decoupled Snapshot (Evaluated)}
The source container resumes execution immediately after memory dumping (\texttt{KeepRunning: true}) while Buildah packages and pushes the image ($T_{\text{build}} + T_{\text{push}}$). 

This minimizes client blackout to $T_{\text{blackout}} \approx T_{\text{restore}}$ ($797$--$1078$~ms), but introduces state drift (uncommitted updates):
\begin{equation}
\text{RPO} = \Delta t_{\text{drift}} = t_{\text{kill}} - t_{\text{dump}} \approx T_{\text{build}} + T_{\text{push}} \approx 696\text{ ms}
\end{equation}
The number of uncommitted updates $\Delta S$ lost upon target cutover is bounded by:
\begin{equation}
\Delta S = \int_{t_{\text{dump}}}^{t_{\text{kill}}} \lambda(t) \, dt \approx \lambda \cdot (T_{\text{build}} + T_{\text{push}})
\end{equation}
where $\lambda$ is the state mutation rate. 

\subsubsection{Mode B: Synchronous Stop-and-Copy (Theoretical Reference)}
The source container is paused before dumping and never resumed. This achieves zero state loss ($\text{RPO} \equiv 0$), but expands client blackout to the entire pipeline:
\begin{equation}
T_{\text{blackout}}^{\text{stop-and-copy}} = T_{\text{freeze}} + T_{\text{build}} + T_{\text{push}} + T_{\text{restore}} = T_{\text{total}}
\end{equation}
Empirically, $T_{\text{total}}$ spans $1642$--$1935$~ms, which is $27.4\%$--$50.1\%$ \textit{worse} than native cold reschedule ($1289$~ms). This establishes the fundamental trade-off: decoupling sacrifices $\approx 696$~ms of state freshness to achieve sub-second client cutover blackout.

\subsection{State Rollback and Phantom Data Risks}
In Mode A, clients that received responses between $t_{\text{dump}}$ and $t_{\text{kill}}$ observed state that is subsequently rolled back upon target restoration. In our experiments, clients observed counter values reaching $60$ (Run 1) and $85$ (Run 2), but target execution resumed at $57$ and $79$, respectively. For transactional workloads, this represents an observable time rollback risk that requires idempotent transaction journals or external write-ahead logs (WAL) to resolve.

\subsection{Analytical Scalability Model for AWS Spot Preemption}
Live migration on AWS EC2 Spot instances must complete within the strict 120-second preemption notice:
\begin{equation}
T_{\text{total}}(M_{\text{RSS}}) < 120\text{ seconds}
\end{equation}
Unlike idealized models that assume constant packaging times, all four pipeline stages scale with resident set size ($M_{\text{RSS}}$):
\begin{align}
T_{\text{total}}(M) = &\ \frac{M}{B_{\text{IO}}} + \left(\frac{M}{B_{\text{tar}}} + t_{\text{oci}}\right) \nonumber \\
&+ \frac{M}{B_{\text{net}}} + \left(\frac{M}{B_{\text{restore}}} + t_{\text{runc}}\right)
\end{align}
where $B_{\text{IO}} \approx 125$~MB/s (EBS gp3 baseline), $B_{\text{net}} \approx 250$~MB/s (conservative sustained baseline for \texttt{m7i-flex.large}), $B_{\text{tar}} \approx 200$~MB/s, and $B_{\text{restore}} \approx 150$~MB/s. \section{Empirical Evaluation}

\subsection{Experimental Setup}
The testbed was deployed on AWS EC2 in region \texttt{eu-central-1} (Frankfurt) within a private VPC:
\begin{itemize}
    \item \textbf{Control Plane:} 1x \texttt{c7i-flex.large} (2 vCPU, 4~GB RAM, Ubuntu 24.04 LTS, Linux 6.8).
    \item \textbf{Worker Nodes:} 2x \texttt{m7i-flex.large} (2 vCPU, 8~GB RAM).
    \item \textbf{Background Contention:} The full 11-microservice Google Online Boutique suite was continuously executed across the worker nodes to generate realistic CPU, memory, and network noisy-neighbor interference.
    \item \textbf{Target Workload:} An in-memory stateful service executing a 10~Hz memory heap counter.
    \item \textbf{Probing Engine:} An external HTTP prober querying the Cilium Ingress at 50~Hz (20~ms sampling intervals) to detect disruption windows.
\end{itemize}

\subsection{Detailed Analysis of Results}
\begin{enumerate}
    \item \textbf{Cutover Blackout vs. Cumulative Disruption:} 
    In Run 2, the cutover blackout window was reduced to \textbf{797~ms} ($\pm 20$~ms), representing a \textbf{38.2\% reduction} relative to native cold reschedule (1289~ms). Across both runs, mean cutover blackout was $937.5$~ms (a 27.2\% improvement). 
    However, when factoring in the freeze stutter ($T_{\text{freeze}} = 147$--$159$~ms), cumulative disruption was $944$~ms (Run 2, a 26.8\% improvement) and $1237$~ms (Run 1, a 4.0\% improvement).
    \item \textbf{RPO and State Drift Verification:} 
    In native eviction, the process state was entirely lost ($43544 \to 8$). Under CRIU migration, state continuity was preserved across nodes with a bounded rollback: $60 \to 57$ in Run 1 ($\Delta S = 3$) and $85 \to 79$ in Run 2 ($\Delta S = 6$). The measured loss of 6 updates in Run 2 is consistent with the theoretical prediction of equation (5) ($\lambda \cdot \Delta t_{\text{drift}} = 10 \times 0.696 \approx 7$). The lower loss in Run 1 ($\Delta S = 3$) reflects clock quantization and asynchronous pod teardown timing.
    \item \textbf{Measurement Resolution:} The observation that $T_{\text{blackout}} = 797$~ms was marginally lower than CRI-O's logged $T_{\text{restore}} = 798$~ms falls well within the $\pm 20$~ms probing resolution.
\end{enumerate}

\section{Related Work}
\subsection{Virtual Machine and Container Live Migration}
Live migration was formalized at the hypervisor layer by Clark et al. \cite{clark2005}, utilizing iterative pre-copying of memory pages. In container virtualization, Stoyanov and Kollingbaum \cite{stoyanov2018} evaluated CRIU-based migration bottlenecks, showing that network transfer of memory pages dominates migration time. Nadgowda et al. \cite{nadgowda2017} developed Voyager to enable complete container migration across clouds. Reber \cite{reber2022} spearheaded the integration of checkpoint-restore mechanisms natively into Kubernetes via KEP-2008. Our study builds upon KEP-2008 by demonstrating end-to-end multi-node pod migration over production OCI registries.

\subsection{Service Mesh Architectures}
Traditional service meshes inject sidecars into application pod namespaces. Recent architectures, notably Cilium eBPF Service Mesh \cite{cilium}, migrate layer-7 routing to node-level proxies. We show that sidecar-free architectures eliminate in-pod loopback socket dependencies, resolving a primary impediment to container checkpointing.

\section{Threats to Validity and System Limitations}
\begin{enumerate}
    \item \textbf{Exploratory Sample Size:} The empirical results represent a dual-hop case study ($n=2$ per path). While sufficient to demonstrate architectural viability and state continuity, large-scale statistical campaigns ($N \ge 50$) are necessary to establish rigorous confidence intervals and tail latencies ($p95, p99$).
    \item \textbf{State Rollback in Decoupled Mode:} Mode A incurs an RPO of $\approx 696$~ms. Applications requiring strict zero-loss must either accept stop-and-copy blackout ($> 1.6$~s) or implement application-level WAL.
    \item \textbf{Memory Scalability Bounds:} Single-pass dumping is limited to workloads with moderate heap sizes ($\le 4$~GB). Multi-gigabyte heaps require iterative dirty-page pre-copying.
    \item \textbf{L4 Protocol Scope:} Our evaluation utilized an HTTP-based stateful service behind an L7 ingress proxy. Workloads relying on direct long-lived L4 TCP or raw UDP connections require complementary connection migration mechanisms.
\end{enumerate}

\section{Conclusion}
This paper presented an empirical evaluation of snapshot-consistent live migration for stateful containers in Kubernetes using CRI-O, CRIU, and sidecar-free Cilium eBPF. The architecture achieves sub-second cutover blackout (797~ms) and 4.0\%--26.8\% lower cumulative disruption than cold restart, while preserving in-memory state with a bounded RPO ($\approx 696$~ms). Future work will incorporate iterative pre-copying to enable zero-RPO migration on multi-gigabyte stateful workloads.
