\begin{abstract}
Stateful singleton containers lacking distributed consensus lose volatile heap state during Kubernetes node maintenance and cloud Spot instance preemptions. We evaluate an automated, snapshot-consistent pod migration pipeline coordinating CRIU (v4.3), the Kubelet Checkpoint API (KEP-2008), Buildah OCI packaging, CRI-O (v1.31), and Cilium eBPF routing across AWS EC2 nodes. Across 36 decoupled migrations compared against 20 native cold reschedules of a stateful service, median cutover blackout is 1064.5~ms versus 1019.0~ms (+4.5\%), while sample means show an overhead of 125.4~ms (+12.5\%, $1132.4 \pm 241.1$~ms vs. $1007.0 \pm 231.2$~ms, 95\% CI: $[-6.7, +257.4]$~ms; Hodges-Lehmann difference: 136.0~ms; Mann-Whitney $U = 252.5, p = 0.0660$). Paired concurrent probing shows external recovery via Service follows operator reporting with a mean lag of $+15.8$~ms (95\% CI $[+11.0, +20.6]$~ms) for CRIU and $+18.5$~ms ($[+12.5, +24.5]$~ms) for cold (per-run range over all 56 runs: $-12$ to $+48$~ms), consistent with sampling jitter of 50~ms polling and 20~ms probing. Blackout variance is governed by Kubelet status reporting (1~s PLEG relisting and status updates) rather than container re-instantiation, with CRI-O unfreezing at 478--516~ms. In exploratory scaling up to 1024~MB (1~GB), uncompressed Buildah packaging slashes build time from 32.06~s to 13.74~s ($2.3\times$), completing source evacuation in 36.78~s within the 120~s Spot deadline with 100\% SHA-256 bit integrity, while writeback throughput (137.9~MiB/s) is consistent with EBS gp3 baseline storage limits (125~MiB/s). Finally, single-container KEP-2008 checkpointing severs in-pod loopback sockets, favoring node-level eBPF routing.
\end{abstract}

\section{Introduction}
Kubernetes manages workloads under the foundational assumption that container instances are ephemeral and stateless \cite{burns2016borg}. When worker nodes undergo kernel maintenance (\texttt{kubectl drain}) or cloud virtual machines are reclaimed, stateless microservices maintain availability by spinning up replacement replicas before terminating old instances (\texttt{maxSurge}).

However, critical production classes maintain large, mutable in-memory heaps without built-in distributed consensus:
\begin{enumerate}
    \item \textbf{Scientific \& Numerical Solvers:} Iterative physics simulations, linear algebra solvers, and legacy C++/Python runtimes accumulating state over hours.
    \item \textbf{Warm ML Inference Caches \& Aggregators:} High-dimensional embedding buffers, key-value transformer caches, and session aggregators where rebuilding state from cold storage imposes severe warm-up latency.
\end{enumerate}

Deploying these workloads on Amazon Web Services (AWS) EC2 Spot instances yields 70--90\% compute cost savings \cite{netflix_spot, sharma2016flint}, but subjects pods to abrupt reclamation with a 120-second termination notice \cite{aws_spot}. Standard eviction issues \texttt{SIGTERM} followed by \texttt{SIGKILL}, destroying volatile RAM. Offloading state to external tiers such as Redis \cite{redis_latency} prevents data loss, but incurs intrusive architectural refactoring and replaces nanosecond memory dereferences with network roundtrips.

Userspace checkpoint/restore via CRIU \cite{criu} provides an application-transparent alternative. In hypervisor literature, ``live migration'' classically refers to iterative pre-copy schemes \cite{clark2005} that track dirty pages via hardware MMU page tables, streaming memory while the virtual machine executes to achieve millisecond cutovers. In container environments lacking hardware virtualization traps, process-level live migration via CRIU and Kubernetes KEP-2008 \cite{reber2022} is operationally distinct. In this paper, we use the term \textit{checkpoint/restore-based container migration} to denote cross-node state transfer that preserves running process heaps and listening sockets without re-executing \texttt{main()} or rebuilding application memory structures, while accepting a sub-second cutover blackout bounded by snapshot serialization and container runtime event loops.

This paper makes four empirical systems contributions:
\begin{itemize}
    \item \textbf{End-to-End Controller:} Privileged DaemonSet operator (\texttt{PodLiveMigration} CRD) automating KEP-2008 checkpointing, Buildah packaging, registry transfer, CRI-O restore, and Cilium eBPF routing across AWS EC2.
    \item \textbf{Statistical Evaluation \& Runtime Profiling ($N = 36$ CRIU vs. $N = 20$ Cold):} Under paired 50~Hz probing, inferential tests ($p = 0.0660$, Hodges-Lehmann: 136.0~ms; Welch's $t = 1.91, p = 0.0628$) and tick regression ($r = 0.9624$) show blackout variance is dominated by Kubelet status reporting. Direct daemon profiling confirms container unfreezing at 478--516~ms; paired concurrent probing shows external recovery via Service follows operator reporting with a mean lag of $+15.8$~ms (95\% CI $[+11.0, +20.6]$~ms) for CRIU and $+18.5$~ms ($[+12.5, +24.5]$~ms) for cold (per-run range over all 56 runs: $-12$ to $+48$~ms), consistent with sampling jitter of 50~ms polling and 20~ms probing.
    \item \textbf{1~GB Scaling \& Packaging Optimization:} In exploratory scaling up to 1024~MB ($N=1$), 100\% SHA-256 bit integrity is verified. We observe writeback throughput (137.9~MiB/s) consistent with EBS gp3 baseline storage limits (125~MiB/s \cite{aws_ebs}) at 1~GB, and show uncompressed Buildah packaging slashes build time from 32.06~s to 13.74~s ($2.3\times$, completing evacuation in 36.78~s within the 120~s Spot deadline).
    \item \textbf{State Reconstruction Benefit \& Sidecars:} We contrast checkpointing against analytical cold state reconstruction (11--30~s for 1~GB), analyze RPO trade-offs, and profile single-container KEP-2008 sidecar loopback constraints.
\end{itemize}

Because a restored pod receives a new Pod IP from the target node's CIDR (\texttt{10.244.2.0/24} $\to$ \texttt{10.244.1.0/24}), \texttt{/etc/criu/default.conf} specifies key flags \cite{criu}:
\begin{itemize}
    \item \texttt{tcp-close}: Restores listening sockets (\texttt{0.0.0.0:8090}) in the \texttt{LISTEN} state while closing established TCP sockets bound to the old Pod IP.
    \item \texttt{skip-in-flight}: Drops transient in-flight TCP handshakes occurring during 50~Hz probing at the instant of \texttt{ptrace} seizure.
    \item \texttt{skip-mnt /run/.containerenv}: Skips CRI-O's transient metadata mount so \texttt{CRImportCheckpoint} mount validation succeeds.
    \item \texttt{ext-unix-sk} and \texttt{shell-job}: Permits dumping external UNIX domain sockets and inherited stdio descriptors.
\end{itemize}

\subsection{Cutover Blackout Definition}
Our benchmark service uses \texttt{HTTP/1.0} behind a Kubernetes Service ClusterIP and Cilium L7 Envoy Ingress without long-hold request buffering. Between source pod deletion ($t_{\text{kill}}$) and target endpoint readiness ($t_4$), incoming requests fail immediately with connection refused or \texttt{HTTP 503}. We define cutover blackout $T_{\text{blackout}}$ strictly as the unavailability window during which probes fail, measured both by the operator clock ($t_4 - t_{\text{kill}}$) and by an external 50~Hz ($\pm 20$~ms) prober as the maximum interval between consecutive \texttt{HTTP 200 OK} responses.

\section{Latency, State Drift, and Evacuation Model}

\subsection{Stage Timestamps and Disruption Decomposition}
The operator records monotonic timestamps around each pipeline step: $t_0$ (pre-checkpoint), $t_1$ (post-dump), $t_2$ (post-build), $t_3$ (post-push), $t_{\text{kill}}$ (pre-delete probe $c_{\text{kill}}$ and pod deletion), and $t_4$ (first \texttt{HTTP 200 OK} from the restored pod):
\begin{align}
T_{\text{freeze}} &= t_1 - t_0, \quad T_{\text{build}} = t_2 - t_1, \quad T_{\text{push}} = t_3 - t_2 \\
T_{\text{restore}} &= t_4 - t_3, \quad T_{\text{blackout}} = t_4 - t_{\text{kill}} = T_{\text{restore}} - t_{\text{probe}}
\end{align}
where $t_{\text{probe}} = t_{\text{kill}} - t_3 \approx 1$--$2$~ms is pre-kill probe latency. Client-perceived disruption consists of source freeze stutter $T_{\text{freeze}}$ (threads paused by \texttt{ptrace}) plus cutover blackout $T_{\text{blackout}}$:
\begin{align}
T_{\text{disruption}} &= T_{\text{freeze}} + T_{\text{blackout}} \\
T_{\text{total}} &= T_{\text{freeze}} + T_{\text{build}} + T_{\text{push}} + T_{\text{restore}}
\end{align}

\subsection{State Drift (RPO), Post-Restore Ticks, and Rollback}
In \textbf{Mode A (Decoupled, \texttt{KeepRunning: true})}, CRI-O unfreezes the source container at $t_1$, allowing it to serve traffic while Buildah packages and pushes the image. State mutations occurring between the snapshot ($S_{\text{ckpt}} \approx c_{\text{dump}} + 1$) and pod deletion ($t_{\text{kill}}$) are lost upon cutover. At mutation rate $\lambda$, Recovery Point Objective (RPO) and lost updates $\Delta S_{\text{lost}}$ are:
\begin{align}
\text{RPO} &= T_{\text{build}} + T_{\text{push}} \\
\Delta S_{\text{lost}} &= c_{\text{kill}} - S_{\text{ckpt}} \approx \lambda \cdot (T_{\text{build}} + T_{\text{push}})
\label{eq:lost}
\end{align}
Workloads with external side effects require idempotency keys or write-ahead logging (WAL).

In \textbf{Mode B (Synchronous Stop-and-Copy, Analytical Projection)}, halting the source container at $t_1$ yields $\text{RPO} \equiv 0$, but extends service unavailability to the entire pipeline ($T_{\text{blackout}}^{\text{stop-and-copy}} = T_{\text{total}}$).

On the target node, \texttt{runc restore} unfreezes the process at $T_{\text{unfreeze}} < T_{\text{restore}}$, and the restored process immediately resumes incrementing from $S_{\text{ckpt}}$. However, the operator only probes $c_{\text{restore}}$ after Kubelet's PLEG loop (1~s period) updates \texttt{Pod.status.phase = Running} at $T_{\text{restore}} = T_{\text{unfreeze}} + \Delta t_{\text{pleg}}$:
\begin{equation}
c_{\text{restore}} - c_{\text{dump}} \approx \lambda \cdot (T_{\text{restore}} - T_{\text{unfreeze}})
\label{eq:post_restore}
\end{equation}

\subsection{Source-Side Spot Evacuation Condition}
When AWS issues a 120-second Spot Interruption Notice, only the source node is terminated at $t = 120$~s; target-side pull and restoration execute on the surviving destination node after $t_3$. Spot survival requires only that worst-case source evacuation $T_{\text{evac}}^{\text{worst}}(M)$ complete within 120~s:
\begin{align}
T_{\text{evac}}^{\text{worst}}(M) = &\ T_{\text{detect}}^{\text{worst}} + T_{\text{freeze}}(M) \nonumber \\
&+ T_{\text{build}}(M) + T_{\text{push}}(M) < 120\text{ s}
\label{eq:spot_evac}
\end{align}
where $T_{\text{detect}}^{\text{worst}} = 5.0$~s accounts for the worst-case detection latency under a 5~s IMDSv2 polling period.

Three crucial findings emerge:
\begin{enumerate}
    \item \textbf{Cutover Blackout and Paired Dual-Prober Validation:} Median operator blackout is 1064.5~ms for CRIU vs. 1019.0~ms for cold restart (+4.5\%), while means show an overhead of 125.4~ms (+12.5\%, $1132.4 \pm 241.1$~ms vs. $1007.0 \pm 231.2$~ms, 95\% CI $[-6.7, +257.4]$~ms; Hodges-Lehmann diff: 136.0~ms; $U = 252.5, p = 0.0660$; Welch's $t(40.8) = 1.91, p = 0.0628$; CIs of cohort means are normal-approximations, whereas the difference CI is Welch $t$-based). The operator polls the Kubernetes apiserver for \texttt{Pod.status.phase = Running} at 50~ms intervals before probing Pod IP directly, while an external 50~Hz prober concurrently queries \texttt{ClusterIP}. Across 56 paired runs, external probing lags operator reporting by a mean of $+15.8$~ms for CRIU (95\% CI $[+11.0, +20.6]$~ms) and $+18.5$~ms for cold restart (95\% CI $[+12.5, +24.5]$~ms; external means diff: 122.7~ms, $U = 252.0, p = 0.0648$). The paired differences ($\sigma = 14.7$~ms for CRIU, $\sigma = 13.8$~ms for cold; per-run range over all 56 runs: $-12$ to $+48$~ms) are consistent with the theoretical sampling convolution of the 50~ms apiserver polling loop ($50/\sqrt{12} \approx 14.4$~ms) and the 20~ms prober grid ($20/\sqrt{12} \approx 5.8$~ms; theoretical joint $\sigma \approx \sqrt{14.4^2 + 5.8^2} \approx 15.5$~ms). Under this sampling model, the observed mean lag reflects tens of milliseconds of Service routing propagation. Because the manifest omits a custom \texttt{readinessProbe}, Kubernetes sets \texttt{PodReady = True} in the same status update as \texttt{Running} (which \texttt{endpointslice-controller} observes via watch without intermediate probe polling).
    \item \textbf{PLEG Dominance and Container Runtime Datapath:} Standard deviations for CRIU ($\sigma = 241.1$~ms) and cold restart ($\sigma = 231.2$~ms) are consistent in order of magnitude with uniform 1~s PLEG relist jitter ($1000 / \sqrt{12} \approx 288.7$~ms). Linear tick regression yields $r = 0.9624$ and x-intercept $T_{\text{unfreeze}} = 537.1$~ms, which aligns with direct CRI-O daemon profiling at 478--516~ms (\texttt{journalctl -u crio: StartContainer}: $\approx 310$~ms pull, $\approx 168$~ms restore). Rather than routing convergence, the residual 261--1151~ms delay after unfreeze is consistent with Kubelet status reporting (interplay of PLEG, status manager, and apiserver synchronization).
    \item \textbf{Trace Dynamics and Methodological Threats:} In Trace \#35 ($51 \to 60 \to 57$), 5 post-restore ticks accumulated during 543~ms of PLEG delay, whereas Trace \#36 ($77 \to 85 \to 79$) experienced only 1 tick. Runs were executed in directional series ($n=20$ \texttt{w1}$\to$\texttt{w2}, $n=16$ \texttt{w2}$\to$\texttt{w1}) with low dirtying rates; non-randomized execution and write-heavy workloads represent threats to validity.
\end{enumerate}

Three systems insights emerge:

\textbf{1) Bit-Exact Restoration within Spot SLA:} In single-trial scaling ($N=1$), all heaps up to 1024~MB restored with 100\% SHA-256 integrity. Under worst-case Spot detection ($T_{\text{detect}}^{\text{worst}} = 5.0$~s) and gzip, source evacuation took 55.09~s (45.9\% of the 120~s SLA). Between 512~MB and 1024~MB, $T_{\text{freeze}}$ jumped $9.8\times$ (coincident with dirty page accumulation) and $T_{\text{push}}$ grew $3.2\times$, while gzip $T_{\text{build}}$ scaled roughly proportionally between 512~MB and 1~GB ($2.0\times$, whereas smaller heaps scaled more steeply, e.g., $5.4\times$ from 128 to 256~MB). Projecting to 2~GB suggests default gzip nears the 120~s deadline ($\approx 105$--$130$~s), requiring uncompressed packaging for multi-gigabyte state.

\textbf{2) EBS gp3 Storage Throughput and Writeback in $T_{\text{freeze}}$:} From 26~MB to 512~MB, $T_{\text{freeze}}$ remains sub-second (144 $\to$ 760~ms) via page cache buffering. At 1~GB, uncommitted dirty memory hits 783.6~MB (\texttt{vm.dirty\_background\_ratio = 10}), triggering kernel flushers. The observed write throughput of $1029.2\text{ MiB} / 7.464\text{ s} \approx 137.9\text{ MiB/s}$ ($144.6\text{ MB/s}$) is consistent with AWS EBS \texttt{gp3} baseline limits (125~MiB/s \cite{aws_ebs}) combined with page caching and co-located service memory pressure.

\textbf{3) Gzip Incompressibility and \texttt{--disable-compression} Speedup:} Incompressible weights produce OCI layers matching heap size. Single-threaded gzip $T_{\text{build}}$ takes 32.060~s at 1~GB. Passing \texttt{--disable-compression} (\texttt{-D}) slashes packaging to \textbf{13.743~s} ($2.3\times$ speedup), trimming evacuation to \textbf{36.78~s} (30.6\% of Spot budget). Over VPC links (1029~MiB pulls in 8.5~s over 1~Gbps baseline), disabling compression is optimal.

\subsection{Why Migrate? Checkpoint Restoration vs. Cold State Rebuild}
A cold reschedule launches an empty container in $\approx 1.0$~s but resets memory state to zero. As an analytical baseline, downloading a 1~GB snapshot from Amazon S3 over 300--800~Mbps takes 10.2--27.3~s transfer plus 1.05--2.5~s deserialization (\textbf{11.2--29.8~s} total recovery).
At 1~GB, migration cutover ($T_{\text{restore}} = 17.328$~s) is comparable to cold reconstruction while bounding state drift (24.3~s under \texttt{-D} vs. 42.6~s under gzip; stop-and-copy: 49.1~s vs. 67.4~s). For heaps $\le 256$~MB, cutover is 0.95--2.11~s (drift: 0.56--3.16~s under \texttt{-D} vs. 0.67--7.48~s under gzip; stop-and-copy: 1.77--5.64~s vs. 1.88--9.96~s). Target restore breaks down into: (1) VPC pull ($\approx 8.5$~s), (2) CRI-O extraction ($\approx 4.8$~s), (3) \texttt{runc/criu restore} unfreezing ($\approx 3.2$~s), and (4) Kubelet status reporting ($\approx 0.8$~s); layer transfer and unpacking govern $>76$\% of restore latency.

\subsection{Architectural Limitations of In-Pod Sidecars}
In a two-container pod with \texttt{stream-server} (:8090) and an Envoy sidecar (:15006) over loopback TCP, KEP-2008 dumped the container in 118~ms and CRI-O restored it on \texttt{k8s-worker-2}. However, because KEP-2008 operates per container and CRIU closes established TCP sockets (\texttt{tcp-close}), the restored application was isolated from its proxy ($T_{\text{blackout}} = \infty$, timing out at 120~s). Node-level routing (Cilium eBPF host routing) decouples proxy lifecycles, avoiding sidecar fate-sharing.

\vspace{-1.5mm}
\section{Related Work}
Clark et al. \cite{clark2005} established VM pre-copy live migration. Voyager \cite{nadgowda2017} and Stoyanov and Kollingbaum \cite{stoyanov2018} combined CRIU with layered storage. Reber \cite{reber2022} standardized KEP-2008 in Kubernetes. Ma et al. \cite{ma2019} analyzed layered storage, and Puliafito et al. \cite{puliafito2019} evaluated fog migration. Recent works address edge and cloud migration: Zhang et al. \cite{kubespt2025} (KubeSPT), Calagna et al. \cite{calagna2024} (edge migration), Bellavista et al. \cite{bellavista2024} (ML workloads), and Poggiani et al. \cite{poggiani2024} (multi-cluster Liqo/CRIU). Complementing these, our study provides an empirical AWS EC2 bottleneck analysis quantifying upstream KEP-2008 and CRI-O bottlenecks: Kubelet status reporting jitter, EBS storage limits, and uncompressed OCI packaging scaling up to 1~GB.

\vspace{-1.5mm}
\section{Limitations, Threats to Validity, and Security}
\textit{Threats to Validity:} We acknowledge key limitations: (1) Workload realism: monotonic counters exhibit minimal dirtying; write-heavy workloads increase dirtying rates ($\dot{M}_{\text{dirty}}$) and drift. Persistent connections require ingress buffering or \texttt{--tcp-established}. Multi-gigabyte heaps benefit from \texttt{criu page-server} streaming. (2) Sample size: heap scaling is exploratory ($N=1$); isolating writeback dynamics requires multi-trial \texttt{tmpfs} and provisioned gp3 controls. (3) Residual delay decomposition: Service recovery follows operator reporting with mean lag $+15.8$~ms (CRIU) and $+18.5$~ms (cold), reflecting tens of milliseconds of Service propagation under 50/20~ms sampling jitter; isolating Kubelet status reporting requires probing Pod IP from $t_3$ rather than awaiting \texttt{Running}. (4) S3 recovery and Mode B are analytical projections. (5) Statistical power: with $N = 36$ and $N = 20$ ($\sigma \approx 240$~ms), 80\% power ($\alpha = 0.05$) detects only differences above $\approx 190$~ms; the observed 125~ms mean difference is inconclusive rather than proof of equivalence. (6) Spot scenario: 120~s headroom is a budget calculation from measured phases and assumed 5~s notice; no real Spot interruption was exercised.
\textit{Security Considerations:} Checkpoint memory dumps contain plaintext application secrets. In our prototype, checkpoint images are pushed to an unauthenticated cluster registry, and the operator runs as a privileged DaemonSet utilizing \texttt{nsenter}. Production deployment necessitates: (1) cryptographic checkpoint encryption at rest, (2) mutual TLS and signed OCI images, and (3) replacing root DaemonSets with scoped capabilities (\texttt{CAP\_CHECKPOINT\_RESTORE} \cite{kernel_cap}, \texttt{CAP\_SYS\_PTRACE}).

\vspace{-1.5mm}
\section{Conclusion}
We presented an empirical study of checkpoint/restore pod migration in Kubernetes using CRI-O, CRIU v4.3, Buildah, and Cilium eBPF. Across $N = 36$ migrations and $N = 20$ cold reschedules on AWS EC2, cutover blackout showed an overhead of 45.5~ms in median (+4.5\%) and 125.4~ms in mean (+12.5\%, 95\% CI $[-6.7, +257.4]$~ms; Hodges-Lehmann diff: 136.0~ms; $p = 0.0660$). Variance is governed by Kubelet status reporting (1~s PLEG relisting and status manager synchronization) rather than container memory instantiation, with CRI-O profiling confirming unfreezing at 478--516~ms, while external recovery via Service follows operator reporting with a mean lag of $+15.8$~ms (CRIU) and $+18.5$~ms (cold; per-run range over all 56 runs: $-12$ to $+48$~ms), consistent with tens of milliseconds of Service propagation and joint 50~ms/20~ms sampling jitter. In exploratory scaling up to 1024~MB, uncompressed packaging slashes build time from 32.06~s to 13.74~s ($2.3\times$, evacuating in 36.78~s within the 120~s Spot deadline) with 100\% SHA-256 integrity, while writeback throughput (137.9~MiB/s) aligns with EBS gp3 baseline storage limits at 1~GB. Checkpointing eliminates external persistence tiers, trading bounded state drift (0.56--3.16~s under \texttt{-D} vs. 0.67--7.48~s under gzip) for 1.77--5.64~s stop-and-copy cutover at $\le 256$~MB under \texttt{-D} (1.88--9.96~s under gzip). Single-container checkpointing severs loopback sidecars, favoring node-level routing.
