\begin{abstract}
While stateless microservices in Kubernetes achieve high availability through multi-replica deployments, rolling updates, and PodDisruptionBudgets, stateful singleton workloads lacking built-in persistence---such as legacy scientific simulations, in-memory session aggregators, and custom stateful inference caches---cannot be trivially replicated without distributed consensus overhead or intrusive application refactoring. When cluster nodes undergo maintenance or ephemeral cloud infrastructure (e.g., Amazon Web Services EC2 Spot instances) is reclaimed via a two-minute preemption notification, the standard Kubernetes eviction lifecycle (\texttt{SIGTERM} followed by \texttt{SIGKILL}) destroys all volatile in-memory heap state.

This paper designs, implements, and evaluates a snapshot-consistent live migration architecture for stateful Kubernetes workloads. The pipeline coordinates the Linux Checkpoint/Restore in Userspace subsystem (CRIU v4.3) via the Kubelet Checkpoint API (KEP-2008), OCI artifact packaging via Buildah, the CRI-O container runtime (v1.31), and a sidecar-free Cilium eBPF networking stack. We formalize and measure the trade-off between client-observed cutover blackout (Recovery Time Objective, RTO) and snapshot state drift (Recovery Point Objective, RPO).

Across $N = 36$ live migrations executed between AWS EC2 worker nodes, the decoupled pipeline achieves a median cutover blackout of 1064.5~ms (minimum 797~ms, mean $1132.4 \pm 241.1$~ms, $p95 = 1532$~ms) and a median process freeze time of 144.0~ms (mean $144.2 \pm 8.4$~ms), yielding a median cumulative disruption of 1203.0~ms (minimum 944~ms) compared to 1289~ms for a cold reschedule baseline that loses 100\% of RAM state. Linear regression across all 36 runs ($r = 0.9624$) reveals that CRI-O unfreezes the restored process at $\approx 537$~ms, while the remaining blackout variance stems from Kubelet's 1~s Pod Lifecycle Event Generator (PLEG) status synchronization loop. Source-side state drift is tightly bounded to $7.5 \pm 0.6$ ticks ($\approx 669$~ms RPO at 10~Hz). Finally, we formulate a self-consistent analytical scaling model for the source-side 120-second Spot evacuation deadline and release all artifacts as open-source.
\end{abstract}

\section{Introduction}
Container orchestration platforms, led by Kubernetes, are built around microservice idempotency and disposable instances \cite{burns2016borg}. In stateless deployments, node drain operations (\texttt{kubectl drain}) and instance preemptions are handled transparently by provisioning replacement pods prior to terminating old replicas via rolling update parameters (\texttt{maxSurge}, \texttt{PodDisruptionBudget}).

However, a distinct class of cloud workloads relies on long-running volatile memory state without built-in distributed checkpointing:
\begin{enumerate}
    \item \textbf{Legacy and Scientific Single-Process Runtimes:} Numerical solvers, physics simulations, and monolithic C++/Python applications that accumulate gigabytes of heap state in RAM without native write-ahead logging.
    \item \textbf{In-Memory Session Aggregators and Caches:} Stateful middleware and warm inference caches where reconstructing in-memory data structures from cold storage incurs prohibitive warm-up latency.
\end{enumerate}

When these stateful singleton workloads run on ephemeral cloud instances---most notably Amazon Web Services (AWS) EC2 Spot instances, which offer 70--90\% cost reductions relative to On-Demand pricing but are subject to preemption with a strict 120-second interruption notice (often preceded by an early EC2 Rebalance Recommendation signal) \cite{netflix_spot, aws_spot}---standard eviction causes complete state loss. When a node is drained, the kubelet issues \texttt{SIGTERM}; upon expiration of \texttt{terminationGracePeriodSeconds} (or hard Spot preemption), \texttt{SIGKILL} destroys the process address space.

A common pattern to avoid state loss is externalizing volatile variables to an in-memory data store such as Redis \cite{redis_latency}. While effective for shared state across replicas, externalizing internal process memory requires intrusive source-code refactoring and replaces nanosecond-scale local RAM accesses with sub-millisecond network round-trips across nodes.

Container checkpoint/restore offers an application-transparent alternative \cite{stoyanov2018, nadgowda2017, criu}. In this paper, we evaluate an end-to-end live migration pipeline built on native Kubernetes primitives. Our contributions are:
\begin{itemize}
    \item \textbf{Decoupled Migration Pipeline:} We implement an automated DaemonSet operator combining KEP-2008 checkpointing \cite{reber2022}, Buildah OCI packaging, CRI-O v1.31 restoration, and Cilium eBPF routing across AWS EC2 nodes without modifying application code.
    \item \textbf{Empirical Statistical Characterization ($N = 36$):} We evaluate 36 back-and-forth live migrations, decomposing client-perceived disruption into source-side freeze latency ($T_{\text{freeze}}$), target-side container restoration ($T_{\text{unfreeze}} \approx 537$~ms), and Kubelet PLEG status propagation delay ($\Delta t_{\text{pleg}}$).
    \item \textbf{RTO vs. RPO Trade-off and Time-Rollback Analysis:} We formalize both decoupled (\texttt{KeepRunning: true}) and synchronous stop-and-copy modes, explaining the relationship between source-side state drift ($\Delta S_{\text{lost}}$) and post-restore target execution ($\Delta S_{\text{post-restore}}$).
    \item \textbf{Source-Side Spot Evacuation Scaling Model:} We derive an affine latency scaling model calibrated to empirical fixed overheads and evaluate source-side evacuation feasibility under the 120-second Spot deadline for heaps from 26~MB to 8~GB.
\end{itemize}

\section{System Architecture}

\subsection{Pipeline Overview and CRIU Configuration}
The migration architecture integrates five components on Ubuntu 24.04 LTS (Linux kernel 6.8): CRIU v4.3 \cite{criu}, the Kubelet Checkpoint API (KEP-2008) \cite{reber2022}, the CRI-O runtime (v1.31) configured with the \texttt{runc} OCI runtime, Buildah for OCI image packaging, and Cilium 1.16 in \texttt{kubeProxyReplacement} mode.

To allow a checkpointed container to restore inside a new network namespace with a different Pod IP on the target node, \texttt{/etc/criu/default.conf} is configured with five directives \cite{criu}:
\begin{itemize}
    \item \texttt{tcp-close}: Restores listening sockets (\texttt{0.0.0.0:8090}) in the \texttt{LISTEN} state while closing any established sockets that are bound to the old Pod IP.
    \item \texttt{skip-in-flight}: Instructs CRIU to ignore transient in-flight TCP connection handshakes occurring during active 50~Hz probing at the moment of \texttt{ptrace} seizure.
    \item \texttt{skip-mnt /run/.containerenv}: Excludes CRI-O's transient metadata file mount, preventing mountpoint validation failures during \texttt{CRImportCheckpoint}.
    \item \texttt{ext-unix-sk} and \texttt{shell-job}: Permits serialization of external UNIX domain sockets and container stdio descriptors.
\end{itemize}

\subsection{Network Cutover and Blackout Definition}
When a pod migrates from \texttt{k8s-worker-1} (\texttt{10.244.2.0/24}) to \texttt{k8s-worker-2} (\texttt{10.244.1.0/24}), its Pod IP changes. Our test workload serves \texttt{HTTP/1.0} responses (closing the TCP connection after each reply) behind a Kubernetes Service ClusterIP and Cilium L7 Envoy Ingress without long-hold request buffering.

Consequently, during the cutover interval between source pod deletion ($t_{\text{kill}}$) and target endpoint readiness ($t_{\text{ready}}$), probes arriving at the Service or Ingress fail immediately (connection refused / \texttt{HTTP 503}). We define the cutover blackout window $T_{\text{blackout}}$ strictly as the unavailability interval during which consecutive probes fail—measured both internally by the operator clock ($t_{\text{ready}} - t_{\text{kill}}$) and externally as the maximum time gap between consecutive \texttt{HTTP 200 OK} responses on a 50~Hz ($\pm 20$~ms) prober.

\subsection{Rationale for Sidecar-Free Networking}
Kubelet's Checkpoint API (\texttt{POST /checkpoint/\{ns\}/\{pod\}/\{container\}}) checkpoints an individual container rather than an entire pod \cite{reber2022}. In a traditional sidecar service mesh (e.g., Istio), the \texttt{istio-proxy} Envoy container runs as a separate container sharing the pod's network namespace (\texttt{netns}) and intercepting traffic via pod-local \texttt{iptables} rules and \texttt{127.0.0.1} loopback connections.

We hypothesize and argue from an architectural standpoint that sidecar-free eBPF networking (Cilium) simplifies container checkpointing for two reasons: (i) checkpointing only the application container leaves behind the sidecar's \texttt{iptables} NAT state and any persistent application-to-sidecar loopback sockets; and (ii) Cilium places L7 Envoy proxying and eBPF socket routing at the host level outside the pod namespace, keeping the container's \texttt{netns} clean. Confirming this experimentally against an Istio sidecar baseline and evaluating persistent \texttt{HTTP/1.1} keep-alive connections remain part of our future work.

\section{Mathematical Latency, Drift, and Scalability Model}

\subsection{Latency Decomposition and Timestamp Semantics}
In our operator implementation (\texttt{05-live-migration-operator.yaml}), timestamps are recorded sequentially around each stage: $t_0$ (before checkpoint API call), $t_1$ (after checkpoint tar creation), $t_2$ (after Buildah commit), $t_3$ (after registry push), $t_{\text{kill}}$ (after the pre-delete counter probe $c_{\text{kill}}$, immediately before \texttt{DELETE /pods}), and $t_4$ (upon the first \texttt{HTTP 200 OK} from the restored pod after Kubelet reports \texttt{phase == Running}).

The stage durations are therefore:
\begin{align}
T_{\text{freeze}} &= t_1 - t_0, \quad T_{\text{build}} = t_2 - t_1, \quad T_{\text{push}} = t_3 - t_2 \\
T_{\text{restore}} &= t_4 - t_3, \quad T_{\text{blackout}} = t_4 - t_{\text{kill}} = T_{\text{restore}} - t_{\text{probe}}
\end{align}
where $t_{\text{probe}} = t_{\text{kill}} - t_3 \approx 1\text{--}2$~ms is the latency of the pre-delete HTTP probe used to read $c_{\text{kill}}$. This explains why operator-logged $T_{\text{blackout}}$ is consistently $1\text{--}2$~ms shorter than $T_{\text{restore}}$ (e.g., $797$~ms vs. $798$~ms, and $1078$~ms vs. $1080$~ms).

Total client-perceived disruption combines the source-side freeze stutter (when threads are halted by \texttt{ptrace} and incoming requests stall in kernel socket queues) and the cutover blackout:
\begin{equation}
T_{\text{disruption}} = T_{\text{freeze}} + T_{\text{blackout}}
\end{equation}
while total end-to-end orchestration duration is:
\begin{equation}
T_{\text{total}} = T_{\text{freeze}} + T_{\text{build}} + T_{\text{push}} + T_{\text{restore}}
\end{equation}

\subsection{Decomposing Target Restoration and Counter Semantics}
The operator logs three counter samples per migration: $\text{Counter}(c_{\text{dump}} \to c_{\text{kill}} \to c_{\text{restore}})$, where:
\begin{itemize}
    \item $c_{\text{dump}}$ is sampled on the source pod immediately prior to $t_0$.
    \item $c_{\text{kill}}$ is sampled on the source pod at $t_{\text{kill}}$ (after $T_{\text{freeze}} + T_{\text{build}} + T_{\text{push}}$).
    \item $c_{\text{restore}}$ is sampled on the target pod at $t_4$ (after Kubelet transitions the target pod to \texttt{status.phase == Running}).
\end{itemize}

Because CRI-O invokes CRIU with \texttt{KeepRunning: true}, the source process continues incrementing at rate $\lambda = 10$~Hz during $T_{\text{build}} + T_{\text{push}}$ (and during the brief pre-seizure setup inside $T_{\text{freeze}}$). If the checkpoint captures state $S_{\text{ckpt}} \approx c_{\text{dump}} + 1$, the true number of source updates lost at cutover is:
\begin{equation}
\Delta S_{\text{lost}} = c_{\text{kill}} - S_{\text{ckpt}} \approx \lambda \cdot (T_{\text{build}} + T_{\text{push}})
\label{eq:lost}
\end{equation}
Correspondingly, the Recovery Point Objective (RPO) is:
\begin{equation}
\text{RPO} = \Delta t_{\text{drift}} = T_{\text{build}} + T_{\text{push}}
\label{eq:rpo}
\end{equation}

Crucially, why is $c_{\text{restore}}$ strictly greater than $c_{\text{dump}}$ (e.g., $51 \to 60 \to 57$ in Run 1 and $77 \to 85 \to 79$ in Run 2)? On the target node, CRI-O and \texttt{runc restore} unfreeze the container at time $T_{\text{unfreeze}}$ after $t_3$, at which point the restored Python thread \textit{immediately resumes incrementing from $S_{\text{ckpt}}$ at 10~Hz}. However, the operator cannot probe the target pod IP until Kubelet's Pod Lifecycle Event Generator (PLEG, which relists container states on a 1~s periodic cycle) updates \texttt{Pod.status.phase = Running} in \texttt{kube-apiserver} at time $T_{\text{restore}} = T_{\text{unfreeze}} + \Delta t_{\text{pleg}}$. During $\Delta t_{\text{pleg}}$, the restored process accumulates $\Delta S_{\text{post-restore}}$ new ticks on the target node:
\begin{equation}
c_{\text{restore}} - c_{\text{dump}} \approx \lambda \cdot (T_{\text{restore}} - T_{\text{unfreeze}})
\label{eq:post_restore}
\end{equation}
Consequently, the difference $c_{\text{kill}} - c_{\text{restore}}$ ($3$ in Run 1; $6$ in Run 2) is \textit{not} the number of lost updates $\Delta S_{\text{lost}}$, but rather $\Delta S_{\text{lost}} - \Delta S_{\text{post-restore}}$.

\subsection{RTO vs. RPO: Decoupled vs. Stop-and-Copy}
In \textbf{Mode A (Decoupled, \texttt{KeepRunning: true})}, the source serves traffic during $T_{\text{build}} + T_{\text{push}}$, yielding $\text{RPO} = T_{\text{build}} + T_{\text{push}}$ ($\approx 669$~ms median) and $T_{\text{blackout}} \approx T_{\text{restore}}$. Clients reading state between $t_1$ and $t_{\text{kill}}$ observe counter values up to $c_{\text{kill}}$ that roll back to $S_{\text{ckpt}}$ when the target starts; transactional workloads therefore require an external write-ahead log (WAL) or idempotency keys.

In \textbf{Mode B (Synchronous Stop-and-Copy, Analytical Reference)}, stopping the source container prior to dumping eliminates state drift ($\text{RPO} \equiv 0$, $\Delta S_{\text{lost}} \equiv 0$), but extends service unavailability to the entire pipeline ($T_{\text{blackout}}^{\text{stop-and-copy}} = T_{\text{total}}$, median $1878.0$~ms, or $45.7\%$ slower than cold reschedule).

\subsection{Source-Side Scalability Model for AWS Spot Preemption}
When an AWS EC2 Spot instance receives a 120-second interruption notice, only the \textit{source node} is terminated at $t = 120$~s. Once the checkpoint image is pushed to the registry ($t_3$), source evacuation is complete; target-side pull and restoration ($T_{\text{restore}}$) proceed on the surviving destination node. Thus, the Spot deadline applies strictly to the \textbf{source-side evacuation time} $T_{\text{evac}}(M)$:
\begin{align}
T_{\text{evac}}(M) = &\ T_{\text{detect}} + T_{\text{freeze}}(M) \nonumber \\
&+ T_{\text{build}}(M) + T_{\text{push}}(M) < 120\text{ s}
\label{eq:spot_evac}
\end{align}
where $T_{\text{detect}} = 2.50$~s is the mean detection latency for a 5~s IMDSv2 poll interval. We model each stage as an affine function of dumpable heap size $M$ (in MB), separating fixed orchestration overheads from bandwidth-bound transfer:
\begin{align}
T_{\text{freeze}}(M) &= t_{\text{dump},0} + \frac{M}{B_{\text{IO}}}, \quad T_{\text{build}}(M) = t_{\text{build},0} + \frac{M}{B_{\text{tar}}} \label{eq:scale1} \\
T_{\text{push}}(M) &= t_{\text{push},0} + \frac{M}{B_{\text{net}}} \label{eq:scale2a} \\
\text{RPO}(M) &= T_{\text{build}}(M) + T_{\text{push}}(M) \label{eq:scale2b} \\
T_{\text{restore}}(M) &= t_{\text{restore},0} + \frac{M}{B_{\text{net}}} + \frac{M}{B_{\text{restore}}} \label{eq:scale3} \\
T_{\text{total}}(M) &= T_{\text{freeze}}(M) + \text{RPO}(M) + T_{\text{restore}}(M) \label{eq:scale4}
\end{align}
Note that $T_{\text{restore}}(M)$ explicitly includes both pulling the image over the network ($M / B_{\text{net}}$) and unpacking/mapping pages on the target node ($M / B_{\text{restore}}$). Calibrating fixed overheads to our $N = 36$ empirical medians at $M = 26$~MB gives $t_{\text{dump},0} = 0.04$~s, $t_{\text{build},0} = 0.24$~s, $t_{\text{push},0} = 0.19$~s, and $t_{\text{restore},0} = 0.79$~s, with conservative sustained uncached bandwidths $B_{\text{IO}} = 125$~MB/s (EBS \texttt{gp3}), $B_{\text{tar}} = 200$~MB/s, $B_{\text{net}} = 250$~MB/s (2~Gbps sustained on \texttt{m7i-flex.large}), and $B_{\text{restore}} = 150$~MB/s. Every entry in Table~\ref{tab:scaling} is computed directly from Eqs.~(\ref{eq:spot_evac})--(\ref{eq:scale4}).

\section{Empirical Evaluation}

\subsection{Experimental Setup}
The testbed was deployed on AWS EC2 in \texttt{eu-central-1} (Frankfurt):
\begin{itemize}
    \item \textbf{Nodes:} 1x \texttt{c7i-flex.large} control plane (\texttt{10.10.1.10}, hosting the local OCI registry \texttt{:5000} and Cilium Ingress) and 2x \texttt{m7i-flex.large} workers (\texttt{k8s-worker-1}, \texttt{k8s-worker-2}).
    \item \textbf{Background Contention:} All 11 microservices of the Google Online Boutique suite were deployed across the worker nodes to create realistic multi-tenant CPU, memory, and CNI control-plane contention.
    \item \textbf{Target Workload:} \texttt{live-stream-pod} running an in-memory 10~Hz counter on port 8090 (\texttt{python:3.12-slim} pre-pulled on both workers).
\end{itemize}

\subsection{Analysis of Findings}
\begin{enumerate}
    \item \textbf{Source-Side Determinism vs. Target-Side PLEG Variance:} Across all $N = 36$ runs, source-side stages exhibit tight determinism: $T_{\text{freeze}} = 144.2 \pm 8.4$~ms, $T_{\text{build}} = 369.0 \pm 16.7$~ms, and $T_{\text{push}} = 294.9 \pm 12.4$~ms. In contrast, $T_{\text{restore}}$ spans $798$--$1688$~ms ($\text{SD} = 241.1$~ms; range $890$~ms).
    \item \textbf{Proof of Unfreeze Timing via Counter Regression:} Performing ordinary least-squares regression of $(c_{\text{restore}} - c_{\text{dump}})$ against $T_{\text{restore}}$ across all $N = 36$ runs confirms Eq.~(\ref{eq:post_restore}) with Pearson correlation $r = 0.9624$, yielding slope $\hat{\lambda} = 9.96$~ticks/s (matching the 10.0~Hz timer) and x-intercept $T_{\text{unfreeze}} = 537.1$~ms. Thus, CRI-O and \texttt{runc restore} actually unfreeze the container on the target node in $\approx 537$~ms; the remaining $261$--$1151$~ms of $T_{\text{restore}}$ is Kubelet's 1~s PLEG status sync delay before reporting \texttt{phase == Running}.
    \item \textbf{Resolution of the Run 1 vs. Run 2 Counter Paradox:} Across all $N = 36$ runs, $c_{\text{kill}} - c_{\text{dump}}$ is tightly bounded between $7$ and $9$ ticks (median $7.0$, mean $7.5 \pm 0.6$), matching Eq.~(\ref{eq:lost}). In Trace \#35 ($51 \to 60 \to 57$, $T_{\text{restore}} = 1080$~ms), the source incremented $9$ times ($51 \to 60$), and after unfreezing at $\approx 537$~ms on the target node, the restored process ticked $\approx 5$ times during the $543$~ms PLEG wait ($52 \to 57$). In Trace \#36 ($77 \to 85 \to 79$, $T_{\text{restore}} = 798$~ms), the PLEG wait was only $261$~ms ($798 - 537$~ms), so the restored counter ticked only $\approx 1$--$2$ times ($78 \to 79$).
\end{enumerate}

\section{Related Work}
Clark et al. \cite{clark2005} introduced iterative pre-copy live migration for virtual machines. In container environments, Stoyanov and Kollingbaum \cite{stoyanov2018} evaluated CRIU migration overhead and image caching, while Nadgowda et al. \cite{nadgowda2017} presented Voyager, unifying CRIU memory checkpointing with union filesystem data migration in Docker. Reber \cite{reber2022} integrated forensic container checkpointing into Kubernetes via KEP-2008. Our work extends KEP-2008 into an automated node-to-node migration pipeline over CRI-O and Cilium eBPF \cite{cilium}, quantifying the interplay between CRIU freeze time, OCI registry packaging, and Kubelet PLEG readiness latency.

\section{Threats to Validity and System Limitations}
\begin{enumerate}
    \item \textbf{Single-Run Cold Baseline \& Analytical Mode B:} While CRIU migration is evaluated across $N = 36$ runs, the native cold reschedule baseline ($1289$~ms) was captured as a single reference run, and Mode B (stop-and-copy) is derived analytically from the measured stage components. Multi-run baselines Including multi-replica stateless deployments with \texttt{PodDisruptionBudget} are planned.
    \item \textbf{L4 Connection Closure (\texttt{tcp-close}):} Because \texttt{tcp-close} closes active TCP sockets on restore and our workload uses short-lived \texttt{HTTP/1.0} requests, persistent \texttt{HTTP/1.1} keep-alive, WebSocket, and UDP sessions were not tested.
    \item \textbf{Single-Pass Memory Scaling:} Our empirical runs used a 26~MB container ($5.16$~MB compressed checkpoint). Validating multi-gigabyte heaps and integrating iterative pre-copy (\texttt{criu dump --pre-dump}) are required for large-memory workloads.
\end{enumerate}

\section{Conclusion}
We presented an empirical and analytical evaluation of snapshot-consistent container live migration in Kubernetes using CRI-O, CRIU v4.3, Buildah, and Cilium eBPF. Across $N = 36$ migrations on AWS EC2, the pipeline achieves a median cutover blackout of $1064.5$~ms (best $797$~ms) and median cumulative disruption of $1203.0$~ms (best $944$~ms) with a tightly bounded RPO of $669.0$~ms ($7.5 \pm 0.6$ ticks), while regression analysis ($r = 0.9624$) isolates Kubelet's 1~s PLEG sync loop as the primary source of post-restore tail latency.
